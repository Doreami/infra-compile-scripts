## 三、建表 & 建索引 SQL

### 建表

```sql
CREATE SCHEMA IF NOT EXISTS sift_ns;

CREATE FOREIGN TABLE sift_ns.sift1m (id bigint, vec vector(128))
SERVER iceberg_catalog_server OPTIONS (namespace 'sift_ns', table_name 'sift1m');
```

### Btree 索引

```sql
SELECT iceberg_catalog.create_index(
    'sift_ns', 'sift1m', 'idx_btree_id',
    '["id"]'::jsonb,
    'btree', 'btree',
    '{"key_column":"id"}'::jsonb
);
```

### IVF 向量索引

```sql
SELECT iceberg_catalog.create_index(
    'sift_ns', 'sift1m', 'idx_ivf_vec',
    '["vec"]'::jsonb,
    'ivf_flat', 'ivf',
    '{"num_clusters":1024, "sample_rate":100000}'::jsonb
);
```

索引文件: `indices/default/builtin.ivf_flat_v2_idx_ivf_vec_*.puffin` (502 MB)

> ³ 之前 K=10 单次测 probes=8 为 984ms，与本次独立测试一致。probes 1→64 耗时变化 <1%，完全在测量噪声范围内。

### 测试项 4: Recall@K（前 20 条查询，num_clusters=1024）

**方法**: 取前 20 条 query，对比 IVF 返回的 top-K ID 与 SIFT1M 官方 ground truth（0-based → +1 对齐表 ID）。

| probes | Recall@10 | Recall@100 | 说明 |
|--------|:---------:|:----------:|------|
| 1 | **74.5%** | 72.5% | 基准 |
| 8 | 74.5% | 72.5% | 无变化 |
| 32 | 74.5% | 72.5% | 无变化 |

> **probes 对 recall 无影响**，与耗时结论一致。probes=1 时 FetchK=50 已扫描足够候选集，提高 probes 不增加额外信息。Recall@100 (72.5%) < Recall@10 (74.5%) 符合 ANN 典型特征——最近邻命中率高于远邻。

## 六、性能总览

| 测试项 | 全扫 (ms) | IVF (ms) | 加速比 |
|--------|-----------|----------|--------|
| Btree 点查 | 76 (7/15) | **171** | 0.44x |
| Top-10 | 2,416 | **1,044** | **2.3x** |
| Top-50 | 2,426 | **1,641** | **1.48x** |
| Top-100 | — | ~2,000 | ~1.2x ⁴ |
| Top-500 | 2,428 | **1,657** | **1.47x** |
| Top-1000 | 2,460 | **2,014** | **1.22x** |
| Top-5000 | 2,450 | **2,299** | **1.07x** |
| Top-10000 | 2,470 | **2,223** | **1.11x** |

> ⁴ K=100 时 IVF 速度与全扫接近，加速比仅 ~1.2x

### IVF 耗时-K 曲线

```
耗时(ms)
2400 |                              ●全扫(~2430ms, 几乎不随K变化)
     |
2000 |     ●IVF K=1000
     |   ●IVF K=5000
     |  ●IVF K=10000
1600 | ●IVF K=500
     |●IVF K=50
1200 |
1000 |●IVF K=10
     +----------------------------------------> K
      10  50  100  500  1000  5000  10000
```

> IVF 在 K=10→50 跳升最大（+600ms），之后在 1600-2300ms 区间波动，未出现 7/15 的 ~1700ms 稳定封顶线。

| K | 全扫 7/15 | 全扫 7/16 | IVF 7/15 | IVF 7/16 | 加速比 7/15 | 加速比 7/16 |
|---|-----------|-----------|----------|----------|-------------|-------------|
| 10 | 2,436 ms | 2,416 ms | 839 ms | 1,044 ms | 2.9x | 2.3x |

## 七、总结

1. **全扫耗时稳定**: 7/15 与 7/16 全扫 K=10 差异 <1%，全扫 K=10→10000 耗时几乎不变（~2430→2470ms），瓶颈在 100 万行全量解码
2. **IVF 加速有效但弱于 7/15**: K=10 加速 2.3x vs 7/15 的 2.9x，慢 ~200ms。帧指针编译 + bridge 版本差异可能各占一部分
3. **IVF K≥100 后加速比衰减严重**: K=5000 时仅 1.07x，几乎无优势。与 7/15 的封顶 ~1700ms 不同，本次 IVF 耗时随 K 增长持续上升至 ~2300ms
4. **probes 对耗时和 recall 均无影响**: probes 1→64，耗时变化 <1%，Recall@10 恒为 74.5%。FetchK=50 时 probes 已无边际收益
5. **Recall@10 基准 74.5%**: num_clusters=1024, probes=1, FetchK=50。提高召回需调 FetchK 而非 probes
6. **Btree 点查**: 171ms，瓶颈在 gaussdb 共享内存初始化（火焰图 >40% CPU），非数据读取
