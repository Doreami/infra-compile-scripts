## 二、热点函数分类

> 把所有场景 >0.5% 的函数按 Shared Object 归类

### A. Parquet 数据解码 → libiceberg_rust_bridge.so

| 函数 | IVF K=10 | 全扫 K=10 | 全扫 K=1000 | 作用 |
|------|:--------:|:---------:|:-----------:|------|
| `RleDecoder::get_batch_with_dict` | ~13% | 14.32% | 15.14% | RLE + bit-packing 解码，**最大单点热点** |
| `ListArrayReader::consume_batch` | 13.19% | ~12% | ~12% | 组装 Arrow ListArray，与 RLE 并列最热 |
| `GenericColumnReader::read_records` | ~5% | ~5% | ~5% | 列读取主循环 |
| `GenericRecordReader::read_records` | ~4% | ~4% | ~4% | RecordBatch 适配层 |
| `DictDecoder::get` | ~4% | ~4% | ~4% | 字典解码回调 |

**Parquet 解码管道**:
```
Parquet Page (压缩)
  -> Zstd/Huffman 解压 (B类)
    -> RLE + bit-packing 解码 (RleDecoder, 14-15%)
      -> Repetition Level 解码 (嵌套层级)
      -> Definition Level 解码 (NULL 标记)
    -> ListArrayReader::consume_batch (13%)
      -> Arrow RecordBatch 输出
```

### B. Parquet 底层工具 → libiceberg_rust_bridge.so

| 函数 | IVF K=10 | 作用 |
|------|:--------:|------|
| `HUF_decompress4X2_usingDTable_internal_fast` | 0.65% | Huffman 解压 |
| `ZSTD_decompressSequences` | ~0.5% | Zstd 解压 |

> 压缩/解压占比很低（合计 <2%），因为 SIFT float 向量数据随机性高，压缩率低，大部分数据以未压缩形式存储。

### 3.3 关键发现

**1. 全扫和 IVF 热点完全相同**

Top-5 热点函数一模一样（`RleDecoder`、`ListArrayReader`、`GenericColumnReader`），因为 `libiceberg_rust_bridge.so` 是统一的数据访问层——无论全扫还是索引扫，所有 Parquet I/O 都经过同一套解码管道。

**2. 向量索引搜索开销可忽略不计**

`read_file_rows_addressed` self-time 仅 0.16%，L2 距离计算、k-means 聚类遍历均 <0.1%，火焰图中完全不可见。索引本身已经优化到极致。

**3. 加速比 2.3x 而非理论 100,000x，三因素定量分解**

| 因素 | 解释 | 定量影响 |
|------|------|----------|
| Parquet 页级读取 | 不能按行读取，IVF 仍需解码聚类所在的数据页 (~976 行) | 解码量 = 全扫的 1/1024 |
| 固定开销 | Puffin 索引文件解析 (502MB) + bridge FFI + gaussdb 计划 ≈ 390ms | 占 IVF 总耗时 37% |
| 单行解码成本相同 | 全扫和 IVF 共用 `RleDecoder` / `ListArrayReader` | 单行耗时相同 |

加速比 = 1000000 / (976 + 390/0.0024) ≈ 1000000 / (976 + 162500) ≈ 6.1x（不考虑索引解析 I/O）。实际测量 2.3x 说明索引文件 I/O 占主导。

**4. Btree 点查热点完全不同于向量查询**

btree 场景 Top-4 函数全在 gaussdb（共享内存管理），占 >40% CPU。数据读取本身几乎无开销（1 行）。每次 btree 扫描触发 `CSNLOGShmemInit` + `SimpleLruInit` + `ShmemInitStruct` + `hash_search` 完整初始化链路。

**5. 帧指针编译正确，调用栈完整可读**

对比修复前（`GaussDbThreadMain` 骑在 `libc.so` 上面），现在的调用栈从 `ExecInitVectorSearch` 到 `ListArrayReader::consume_batch` 逐层可追溯。`-fno-omit-frame-pointer` + `force-frame-pointers=yes` 组合生效。

## 四、优化建议

| 优先级 | 方向 | 依据 | 预期收益 | 适用场景 |
|:------:|------|------|:--------:|:--------:|
| **P0** | `list<float>` → `fixed(512)` | `ListArrayReader::consume_batch` 13.19% + Rep/Def Level 解码 ~12% = **25% CPU** 在嵌套类型解析。`fixed(512)` 是 Iceberg 定长原始类型，无需 Rep/Def Level | 消除 25% 解码开销 | 全扫 + IVF |
| **P1** | 内核缺页优化 | [unknown] kernel 占 10-18%，huge page (2MB) + 预读可减少 TLB miss 和缺页次数 | 减少 30-50% 内核开销 | 所有场景 |
| **P2** | btree SLRU 懒初始化 | `CSNLOGShmemInit` 11.57% + `ShmemInitStruct` 10% → 仅在首次访问时初始化 | btree 点查从 171ms → ~50ms | Btree 点查 |
| **P3** | Parquet Row Group 裁剪 | IVF 解码完整聚类 (976 行)，如果 Parquet page 按 row group 对齐可减少解码量 | IVF 解码量减半 (976→~500) | IVF |
| **P4** | 索引文件 mmap 预热 | 冷启动 ~2.2s，其中 502MB 索引文件解析是大头。mmap + 后台预读 | 消除冷启动 | IVF 首次查询 |
