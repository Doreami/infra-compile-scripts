## 一、耗时基准测试

- 耗时来源: `EXPLAIN (ANALYZE)` 的 `Total runtime`
- IVF 冷启动 ~7s（3.6GB 索引加载），warm 后稳定
- 全扫: `SET enable_indexscan = off; SET enable_bitmapscan = off; SET enable_vectorsearch = off;`
- IVF: `SET enable_vectorsearch = on; SET try_vector_engine_strategy = force;`

### K 值曲线

| K     | IVF (warm)  | FullScan | 加速比      |
| ----- |:-----------:|:--------:|:--------:|
| 10    | **7,031ms** | 21,143ms | **3.0×** |
| 50    | 10,788ms    | 20,812ms | 1.9×     |
| 100   | 15,639ms    | 21,164ms | 1.4×     |
| 500   | 15,503ms    | 20,613ms | 1.3×     |
| 1000  | 15,525ms    | 21,532ms | 1.4×     |
| 5000  | 15,730ms    | 20,880ms | 1.3×     |
| 10000 | 15,651ms    | 21,710ms | 1.4×     |

> IVF K 值增大后耗时封顶在 ~15.6s，因为 FetchK=50 限制了实际取的候选数。FullScan 始终 ~21s，与 K 无关（100 万行全量排序）。

### SIFT1M 对比

| 场景            | SIFT (128维) | GIST (960维) | 倍数       |
| ------------- |:-----------:|:-----------:|:--------:|
| IVF K=10 warm | 1,044ms     | 7,031ms     | **6.7×** |
| FullScan K=10 | 2,416ms     | 21,143ms    | **8.8×** |
| 加速比 K=10      | 2.3×        | **3.0×**    | —        |

> 耗时增长接近维度比（960/128=7.5×），符合预期。

### EXECUTE PLAN (IVF K=10)

```
Limit  (actual time=0.068..0.068 rows=10 loops=1)
  ->  Vector Search  (Algorithm=TopK, Metric=L2, TopK=10, FetchK=50)
        ->  Foreign Scan on gist1m
              Iceberg FDW: bridge vector index scan
              Index Name: idx_ivf_vec
              Query Vector Dim: 960
Total runtime: 7031.298 ms
```

> Vector Search 节点仅 0.068ms，实际 7,031ms 消耗在 bridge 内部（索引搜索 + Parquet 解码 + 回表读取），openGauss 侧无感知。

## 二、关键发现

### 1. IVF 有效，加速比 3×

冷启动 ~7s（索引加载）后，IVF K=10 warm 7,031ms vs 全扫 21,143ms。索引本身工作正常，不是之前误判的"加速比消失"。

### 2. 耗时随维度线性增长

GIST/SIFT = 6.7×（IVF）和 8.8×（全扫），接近维度比 7.5×。说明瓶颈是 Parquet 解码 + 索引文件 IO，不是索引搜索本身。

### 3. K 值封顶效应

IVF K≥100 后耗时封顶 ~15.6s，因为 FetchK=50 硬编码限制了每次最多取 50 个候选，无法通过增大 K 突破。

### 4. 冷启动是主要痛点

3.6GB 索引加载占 ~7s，占总耗时 30%（warm 时 7s vs cold 时 ~27s）。Puffin 懒加载（已部分实现）可减少冷启动开销。
