# IVFPQ DOP=64 扩展性分析报告 — 2026-07-20

**编译模式**: Release + 帧指针 (`-fno-omit-frame-pointer`)
**测试环境**: openEuler 24.03, 96核, 723GB, kernel 6.6.0-28
**数据集**: SIFT1M (128-dim), IVFPQ num_clusters=256

---

## 一、测试目的

验证 query_dop 从 1 到 64 的扩展性，对比 **bucket(id, 16)** vs **bucket(id, 64)** 两张表在相同 DOP 下的表现：

1. 16 分区是否在 DOP>8 后已饱和？
2. 增大分区数能否突破饱和点？
3. DOP=64 时瓶颈到底在哪里？

---

- 扫描方式: IVF 索引扫

- 每组合 5 轮取**平均值**（1 轮预热排除冷启动）


## 三、并行 Scaling 对比

### 3.1 16 分区

```
  K      dop=1   dop=2   dop=4   dop=8  dop=16  dop=32  dop=64  1→64
  ─────────────────────────────────────────────────────────────────────
  K=10    4225    2864    1642    1243    1160    1217    1136   3.72×
  K=100   5445    3358    1899    1315    1163    1130    1156   4.71×
  K=10000  6776    3350    1915    1319    1110    1161    1148   5.90×
```

**逐级加速比**：

| K     | 1→2   | 2→4   | 4→8   | 8→16  | 16→32 | 32→64 |
| ----- |:-----:|:-----:|:-----:|:-----:|:-----:|:-----:|
| 10    | 1.48× | 1.74× | 1.32× | 1.07× | 0.95× | 1.07× |
| 100   | 1.62× | 1.77× | 1.44× | 1.13× | 1.03× | 0.98× |
| 10000 | 2.02× | 1.75× | 1.45× | 1.19× | 0.96× | 1.01× |

- **饱和点**: DOP=8，之后加速比趋近 1.0×
- **最优**: DOP=16, K=10 → 1160ms
- DOP=32/64 基本持平，无退化

### 3.2 64 分区

```
  K      dop=1   dop=2   dop=4   dop=8  dop=16  dop=32  dop=64  1→64
  ─────────────────────────────────────────────────────────────────────
  K=10    3635    2445    1790    1661    1970    2812    5189   0.70×
  K=100   4966    3592    2807    2683    2418    2953    5130   0.97×
  K=10000  8217    4912    3607    2762    2527    2993    5197   1.58×
```

**逐级加速比**：

| K     | 1→2   | 2→4   | 4→8   | 8→16      | 16→32     | 32→64     |
| ----- |:-----:|:-----:|:-----:|:---------:|:---------:|:---------:|
| 10    | 1.49× | 1.37× | 1.08× | **0.84×** | **0.70×** | **0.54×** |
| 100   | 1.38× | 1.28× | 1.05× | 1.11×     | **0.82×** | **0.58×** |
| 10000 | 1.67× | 1.36× | 1.31× | 1.09×     | **0.84×** | **0.58×** |

- **饱和点提前到 DOP=4**
- DOP=8→16 开始**减速**（<1.0×），DOP=32→64 每次只有上一级的 ~55%
- DOP=64 严重退化：K=10 比串行慢 43%

### 3.3 直接对比（差值百分比）

```
K=10    dop=1   dop=4   dop=8   dop=16  dop=32  dop=64
──────────────────────────────────────────────────────────
16分区    4225    1642    1243    1160    1217    1136
64分区    3635    1790    1661    1970    2812    5189
差异     -14%    +9%    +34%    +70%   +131%   +357%

K=100
16分区    5445    1899    1315    1163    1130    1156
64分区    4966    2807    2683    2418    2953    5130
差异      -9%    +48%   +104%   +108%   +161%   +344%

K=10000
16分区    6776    1915    1319    1110    1161    1148
64分区    8217    3607    2762    2527    2993    5197
差异     +21%    +88%   +109%   +128%   +158%   +353%
```

（负值 = 64 分区更快，正值 = 16 分区更快）

### 3.4 发现

1. **串行 DOP=1 时 64 分区略优**（K=10: 3635 vs 4225ms, -14%）：分区更细，单分区扫描更快
2. **DOP≥8 时 16 分区全面碾压**：16 分区 DOP=8 的 1243ms 比 64 分区最优值 1790ms 快 44%
3. **64 分区 DOP>8 出现负加速**：每增加一级 DOP，查询反而更慢
4. **DOP=64 灾难**：比 16 分区同 DOP 慢 3~4 倍，比 64 分区串行还慢

## 四、火焰图分析

### 4.1 采样量：CPU 周期消耗对比

perf 采样数反映 CPU 周期总量。在相同查询场景下，采样数越大说明 CPU 做了越多"无用功"。

| 表       | K   | DOP | 采样数        | 查询耗时   | 采样/ms    |
| ------- |:---:|:---:|:----------:|:------:|:--------:|
| 16-part | 10  | 1   | 1,305      | 4225ms | 0.31     |
| 16-part | 10  | 8   | —          | 1243ms | —        |
| 64-part | 10  | 1   | 1,364      | 3635ms | 0.38     |
| 64-part | 10  | 4   | **2,642**  | 1790ms | 1.48     |
| 64-part | 10  | 64  | **24,658** | 5189ms | **4.75** |
| 64-part | 100 | 1   | 2,096      | 4966ms | 0.42     |
| 64-part | 100 | 4   | 4,684      | 2807ms | 1.67     |
| 64-part | 100 | 64  | 15,445     | 5130ms | 3.01     |

> **采样/ms** = 单位时间 CPU 消耗密度。DOP=64 时 4.75 samples/ms vs DOP=1 时 0.38 samples/ms —— CPU 密度暴增 12.5×，但查询反而慢了 43%。

### 4.2 热点函数对比

#### K=10

| 热点函数                           | DOP=1 | DOP=4 (最优) | DOP=64 (退化) | 趋势        |
| ------------------------------ |:-----:|:----------:|:-----------:| --------- |
| bridge tokio runtime scheduler | 9.73% | 6.52%      | 6.61%       | DOP=4 后持平 |
| gaussdb undo::InitUndoZoneLock | 5.55% | 6.37%      | 4.94%       | 占比稳定      |

#### K=100

| 热点函数                               | DOP=1      | DOP=4 (最优) | DOP=64 (退化) | 趋势                         |
| ---------------------------------- |:----------:|:----------:|:-----------:| -------------------------- |
| bridge tokio runtime scheduler     | **15.88%** | 10.57%     | 5.96%       | 高 DOP 反而下降（被 gaussdb 竞争淹没） |
| bridge task list bind_new_task     | 8.48%      | —          | —           | 仅串行出现                      |
| iceberg TableScan::plan_files      | —          | 4.75%      | —           | DOP=4 可见                   |
| **gaussdb undo::InitUndoZoneLock** | —          | —          | **8.84%**   | **DOP=64 成为第一大热点**         |

关键信息：DOP=64 K=100 时，`undo::InitUndoZoneLock` 从无到有跃升为 **8.84% 第一大热点**，而 bridge 开销从 15.88% 降到 5.96%——不是因为 bridge 变快了，而是 gaussdb 侧的竞争成了新的天花板。

### 4.3 火焰图对比解读

#### 64 分区：DOP=4 vs DOP=64（`flame_64part_k10_dop4.svg` vs `flame_64part_k10_dop64.svg`）

| 特征               | DOP=4                                | DOP=64                                |
| ---------------- | ------------------------------------ | ------------------------------------- |
| SVG 大小           | 498 KB                               | **798 KB**                            |
| 火焰图宽度（CPU 总量）    | 较窄                                   | **极宽**（9.3× 采样量）                      |
| streamworker 线程数 | 4                                    | **64**                                |
| 主要热点色块           | bridge tokio (暖色) + distance compute | **大量 gaussdb undo/semaphore（冷色系统调用）** |
| 调用栈形态            | 清晰的分层调用链                             | 碎片化、大量短栈（锁等待）                         |

#### 16 分区 vs 64 分区 串行基线（`flame_16part_k10_serial.svg` vs `flame_64part_k10_serial.svg`）

- 16 分区串行火焰图宽度更宽（更多数据扫描），但 64 分区 bridge 调用栈占比稍高（更碎的分区 → 更多文件打开/关闭开销）
- 两者热点分布相近，64 分区略优的原因：单分区小，Parquet 页读取更快

#### 16 分区 DOP=8（`flame_16part_k10_dop8.svg`）

- 8 个 streamworker 均匀分布，bridge 锁等待占比低
- 火焰图形态干净，无明显的系统调用堆积
- 这是当前架构的最佳形态

### 4.4 退化根因（三层竞争模型）

```
DOP=64 查询执行栈：
┌─────────────────────────────────────────────┐
│ Layer 3: gaussdb coordinator                │
│   LOCAL GATHER 合并 64 路 → 线性开销        │
│   undo::InitUndoZoneLock 64个并发 → 8.84%   │
├─────────────────────────────────────────────┤
│ Layer 2: bridge 数据面                       │
│   BLOCK_ON_LOCK 全局锁 → 64抢1              │
│   tokio scheduler 排队 → 6.61%              │
├─────────────────────────────────────────────┤
│ Layer 1: 存储                                │
│   64 分区 × ~15K 行/分区                     │
│   每分区数据少但文件碎片化严重               │
└─────────────────────────────────────────────┘
```

DOP=4 时三层竞争均未触发：

- Layer 1: 每个 worker 处理 16 个分区，数据量充足
- Layer 2: 4 个 worker 对 bridge 锁竞争轻微
- Layer 3: gaussdb 4 路合并，undo 竞争可忽略

DOP=64 时三层同时饱和：

- Layer 1: 64 分区被 64 worker 瓜分，每 worker 只读 1 个分区，文件碎片开销凸显
- Layer 2: 64 线程争 1 把锁，大量 CPU 空转在 tokio 调度循环
- Layer 3: gaussdb 侧 64 路并发 undo 初始化，`CreateSharedMemoryAndSemaphores` 成为性能杀手

## 五、结论

### 5.1 核心问题回答

| 问题              | 答案                                                  |
| --------------- | --------------------------------------------------- |
| DOP=32/64 有收益吗？ | **没有**。16 分区 DOP=8 即饱和，64 分区 DOP>4 即退化              |
| 分区越多越好吗？        | **不是**。64 分区最优性能比 16 分区差 44%                        |
| 瓶颈在哪？           | 低 DOP: bridge 全局锁；高 DOP: gaussdb undo 竞争 > bridge 锁 |
| 推荐配置            | **16 分区 + DOP=8**                                   |
| DOP=64 为什么更慢？   | CPU 密度 12.5× 但有效工作占比极低——三重竞争吃掉了所有收益                 |

### 5.2 建议

1. **不再测试 DOP>16**：16 分区 + DOP=8 已是 sweet spot
2. **增加分区不能替代 bridge 锁优化**：`BLOCK_ON_LOCK` → per-file 粒度是释放并行的前提
3. **gaussdb 侧需关注**：`undo::InitUndoZoneLock` 在高并发下成为新热点，可能需要 lazy init 或 per-worker 缓存
4. **火焰图已确认**：DOP=64 每毫秒消耗 4.75 个采样点的 CPU，是串行的 12.5 倍——这是花钱买罪受
