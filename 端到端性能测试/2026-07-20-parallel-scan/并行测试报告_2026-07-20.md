## 三、测试方案

### 3.1 测试矩阵

每数据集覆盖以下组合，每组合跑 3 轮取中位数：

| 维度          | 取值                    |
| ----------- | --------------------- |
| `query_dop` | 1, 2, 4, 8            |
| 扫描方式        | IVF 索引扫, FullScan 全表扫 |
| `LIMIT K`   | 10, 100, 10000        |

### 3.2 SQL 模板

**IVF 索引扫**：

```sql
SET query_dop = {dop};
SET enable_vectorsearch = on;
SET try_vector_engine_strategy = force;
EXPLAIN ANALYZE
  SELECT id FROM {ns}.{tbl}
  ORDER BY vec <-> '{qv}'::vector
  LIMIT {k};
```

**FullScan 全表扫**：

```sql
SET query_dop = {dop};
SET enable_indexscan = off;
SET enable_bitmapscan = off;
SET enable_vectorsearch = off;
EXPLAIN ANALYZE
  SELECT id FROM {ns}.{tbl}
  ORDER BY vec <-> '{qv}'::vector
  LIMIT {k};
```

- `{dop}` ∈ {1, 2, 4, 8} — 并行度
- `{k}` ∈ {10, 100, 10000} — Top-K 值
- 查询向量 `{qv}` 取自标准查询集的第 0 条
- 耗时来源：`EXPLAIN ANALYZE` 的 `Total runtime`
- IVF 每 K 值首轮做预热（排除冷启动），后续 3 轮取中位数
- 同时校验 EXPLAIN 计划：`dop=1` 不应出现 `LOCAL GATHER`，`dop>1` 必须出现

### 3.3 加速比公式

```
dop1/dop8 = 耗时(dop=1) / 耗时(dop=8)
```

> 表中"加速比"列统一取串行 vs 最大并行度的比值。例如 SIFT IVF K=10: 4873ms / 1184ms = 4.12×。

## 六、SIFT vs GIST 对比

| 指标             | SIFT (128d) | GIST (960d) |
| -------------- |:-----------:|:-----------:|
| IVF 串行 K=10    | 4.9s        | 39.3s       |
| IVF dop=8 K=10 | 1.2s        | 8.1s        |
| IVF 加速比        | **4.1×**    | **4.8×**    |
| FullScan 加速比   | 1.1×        | 1.0×        |
| 索引构建           | 7.8 min     | 63.2 min    |
| 索引大小           | ~300 MB     | ~9.6 GB     |

### IVFPQ vs IVFFlat（SIFT1M K=10）

| 索引类型 | num_clusters | dop=1 | dop=8 | vs Flat 基线 |
|------|:--:|:--:|:--:|:--:|
| IVFFlat（7/18） | 1024 | **606ms** | - | 基线 |
| IVFPQ（本次） | 256 | 4873ms | **1184ms** | 慢 2.0× |

> IVFPQ 串行比 IVFFlat 慢 8×，来自 PQ 编解码的额外计算（16 个子量化器 × 每向量查码本 + 残差还原）。但 dop=8 后差距缩小到 2×。
>
> IVFPQ 的空间优势：索引 ~300 MB vs IVFFlat ~502 MB（均为 num_clusters=256 时的对比；Flat 1024 时更大）。
>
> **num_clusters 取值说明**：IVFFlat 测试时用 1024 是当时标准配置。IVFPQ 选 256 因为 IVFPQ 默认值为 16，256 已远超默认。如果 IVFPQ 也用 1024，查询性能会更好（每聚类行数从 ~3900 降到 ~976，扫描量降 4×），但索引构建时间也会成倍增长——GIST 在 1024 时跑 30+ 分钟无进展，256 时花了 63 分钟。这是一个训练成本与查询性能的 trade-off。

### 关键发现

1. **IVF-PQ 并行收益显著且跨数据集一致**：SIFT 4.1×, GIST **4.8×** (dop=1 → 8，干净测试)
2. **FullScan 无并行收益**：bridge 数据面全局串行锁封顶，高维场景反而下降
3. **K 值越大加速比越高**：GIST K=10000 加速 5.3× vs K=10 加速 3.5×，说明 rank-merge 阶段受益更大
4. **GIST 索引构建是挑战**：960 维 × 120 子量化器 = 63 分钟，需 nohup 避免 SSH 超时

## 八、已知问题：GIST 索引构建残留文件

### 现象

GIST 的 `create_index` 被多次中断（`pg_terminate_backend`）后，磁盘残留 44 个、共 9.6GB 的 puffin 文件，但 catalog 表中无对应索引记录。

### 根因

1. `create_index` 按分区串行构建（`build_partition_segment` 循环），每分区完成后**立即将 puffin 写入磁盘**
2. 索引元数据注册（写入 `iceberg_catalog.table_indexes`）是**最后一步的事务提交**
3. 如果构建被中断（手动杀 backend / SSH 超时），已写入的 puffin 文件**不会回滚**——它们是磁盘文件，不在 PostgreSQL 事务管理范围内

```
分区 0 写入 puffin ✅
分区 1 写入 puffin ✅
...
分区 7 写入 puffin ✅
分区 8 正在构建... ← pg_terminate_backend 中断
─────────────────────────────────
事务回滚: table_indexes 无记录
磁盘残留: 8 个 puffin 文件（~5GB）永久遗留
```

### 影响

- 磁盘空间泄漏（9.6GB 无法自动回收）
- 表的 `metadata.json` 不引用这些文件 → `remove_orphan_files` 可能无法清除
- 需手动 `rm -rf indices/` + 重导数据才能彻底清理

### 建议

`create_index` 应改为**先写临时目录、全部完成后再原子 rename 到正式目录**，避免残留。
