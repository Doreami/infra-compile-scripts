## 二、SIFT1M — IVF 索引扫

| 指标 | dop=1 (串行) | dop=8 (并行) |
|------|:--:|:--:|
| 查询耗时 | 4873ms | **1184ms** |
| 样本数 | 1377 | 3416 |
| 执行线程 | `worker` (单线程) | `streamworker` (8 线程) |
| Top-1 热点 | ZSTD 10.1% | ZSTD 16.8% |

**分析**：

- 串行时 ZSTD 解压占 10%，但总样本只有 1377 → 查询太快，采样不够密集
- 并行时样本 3416（2.5×），因为 8 个 streamworker 线程在 perf 上同时采样
- ZSTD 占比从 10% → 17%，说明并行下多个 worker **同时在做解压**，CPU 利用率提高
- 并行加速 4.1× 来自 16 分区各由不同 worker 处理，减少单线程数据扫描量

**火焰图结论**：热点不变（ZSTD 解压始终最大），但计算被分摊到 8 个线程，单个 worker 扫描行数从 100 万降到 ~6.25 万。

## 三、SIFT1M — 全表扫描

| 指标 | dop=1 (串行) | dop=8 (并行) |
|------|:--:|:--:|
| 查询耗时 | 2526ms | 2121ms |
| 样本数 | 1909 | 2023 |
| 执行线程 | `worker` | `streamworker` |
| Top-1 热点 | ZSTD 28.0% | ZSTD 22.5% |

**分析**：

- 耗时几乎不变（1.19×），尽管线程从 1→8
- ZSTD 占比从 28% → 22%，说明并行下单个 worker 解压量减少，但**总耗时被 bridge 全局串行锁封顶**
- 样本数相近（1909 vs 2023），说明 8 个 streamworker 的总 CPU 时间与 1 个 worker 相当 → bridge 锁把并行收益全部抵消

**火焰图结论**：并行形态正确（streamworker + LOCAL GATHER），但数据面受 bridge 单锁限制，CPU 无法真正并行。

## 四、GIST1M — IVF 索引扫

| 指标 | dop=1 (串行) | dop=8 (并行) |
|------|:--:|:--:|
| 查询耗时 | 39282ms | **8126ms** |
| 样本数 | 2013 | 6760 |
| 执行线程 | `worker` | `streamworker` |
| Top-1 热点 | [kernel] 9.5% | [kernel] 9.2% |

**分析**：

- GIST 960 维数据量大（每行 3840B），热点从 ZSTD 变为**内核态内存操作**
- 串行时内核 [unknown] 占 9.5%，并行时 9.2% — 内核开销比率不变
- 并行加速 4.8× 来自分区切分：16 分区各处理 ~62.5K 行，单 worker 数据量降为 1/8
- 样本数 6760 vs 2013（3.4×），证明并行下 CPU 利用率显著提高

**火焰图结论**：高维场景瓶颈在内核内存拷贝/缺页，非 ZSTD。并行通过减少单线程数据量获得加速，比 SIFT 收益更大（4.8× vs 4.1×）。

## 五、串行 vs 并行 — 关键差异

### 线程模型变化

| 串行 (dop=1) | 并行 (dop=8) |
|------|------|
| `worker` — gaussdb 主工作线程 | `streamworker` — SMP 并行工作线程 |
| 单线程读全表 | 8 线程各读 1/8 分区 |
| 无 LOCAL GATHER | 有 LOCAL GATHER 收拢结果 |

### 热点函数对比

| 场景 | 热点变化 |
|------|------|
| SIFT IVF | ZSTD 10% → 17%（并行分摊算力） |
| SIFT FullScan | ZSTD 28% → 22%（bridge 锁抵消） |
| GIST IVF | kernel 9.5% → 9.2%（瓶颈不变） |

### 为什么 IVF 加速、FullScan 不加速

```
IVF 路径:  各 worker 独立读取自己的分区 → 索引过滤 + 精排 → LOCAL GATHER 收拢
           ↑ 每 worker 数据量 1/8，计算并行度 ≈ 分区数

FullScan:  各 worker 独立读取自己的分区 → 全量距离计算 → LOCAL GATHER 收拢
           ↑ 数据读取路径共享 bridge 全局锁，8 线程排队 = 无加速
```

## 六、bridge 全局串行锁详解

### 为什么 FullScan 并行无效

设计文档 §9 明确指出：

> bridge 数据面经进程全局锁串行，N 个 worker 的数据面 I/O 全在一把全局锁上排队。

具体机制：
- bridge 内部使用 `BLOCK_ON_LOCK` 保护数据读取路径
- 所有 Parquet 文件解码（ZSTD 解压、Arrow 构造、物化）共享这把锁
- 8 个 streamworker 线程试图同时读数据 → 8 个线程在锁上**串行排队**

这就是火焰图中看到的现象：样本数相近（1909 vs 2023），CPU 利用率没有随线程数增加。

### 为什么 IVF 不受影响

IVF 的瓶颈不在数据读取，而在**距离计算**：

```
FullScan 路径:  [读数据(锁)] → 距离计算 → 排序
                 ↑ 100万行, 瓶颈在锁

IVF 路径:       [读索引(锁)] → 索引过滤 → [读候选行(锁)] → 距离计算 → 精排
                  ↑ 一次               ↑ ~6万行         ↑ 并行分摊
```

IVF 的"读候选行"只需解码 ~6 万行（/分区），锁持有时间短；真正耗时的是距离计算（浮点矩阵乘），这部分在 gaussdb 侧做，不受 bridge 锁限制。并行下 8 个 worker 各自算自己的分区，距离计算天然并行。

### 解除 bridge 全局锁

设计文档的缓解措施：

> bridge 侧 `new_current_thread` runtime + 进程级 `BLOCK_ON_LOCK`

意思是把当前 tokio 单线程 runtime 改为多线程 runtime，同时把进程级锁降为细粒度锁（per-file 或 per-reader），让多个 worker 可以并发读不同的 Parquet 文件。这是 bridge 侧独立课题，不影响 FDW/内核的并行链路。

---

## 七、总结

1. **并行形态正确**：`streamworker` 线程 + `LOCAL GATHER` 正常成形
2. **IVF 受益最大**：索引过滤后单 worker 数据量小，8 线程分摊计算 → 4-5× 加速
3. **FullScan 空转**：bridge 数据面全局串行锁把并行收益全部吃掉
4. **高维 GIST 瓶颈在内核**：960 维内存拷贝主导，与 ZSTD 无关
5. **下一步**：解除 bridge 全局锁 → FullScan 也获得加速；内核内存操作优化 → GIST 整体提速
