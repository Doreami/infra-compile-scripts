## 二、模块归因

```
无压缩 IVF K=10 CPU 分布 (估算):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
gaussdb infra (StatementFlush + ShmemInit + CSNLOG)  ████████████████ ~16%
bridge tokio (scheduler + task management)            ████████ ~5%
bridge SipHash (HashMap operations)                   ██████ ~4%
bridge Parquet decode (FixedLenBinary, no compression)██████ ~6%
kernel (page faults, memory copies)                   ████████████ ~12%
向量距离计算 (L2)                                      ▏ <1%
其他未归类                                             ██████████████████████████████ ~57%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**核心结论**：消除压缩后，没有任何单一热点超过 7%。CPU 被均匀分散到 gaussdb 基础设施、bridge tokio 调度、内存分配、内核缺页等数十个小函数中。**压缩是最后一个"低垂的果实"**，接下来的优化需要系统性改造。

## 三、后续优化路径（按收益×可行性排序）

### P0: 列裁剪 — 跳过 vec 列回表读取

**当前瓶颈**: `materialize_candidates()` 对候选行做全列读取（包括 `vec` 列，512B/行），但 SQL `SELECT id` 只需要 `id`。

**火焰图证据**: SipHash 4.06% 来自 `materialize_candidates` 内部的 HashMap join，Parquet 解码 ~6% 来自多余列的读取。列裁剪后这些同比例缩减。

**读取量对比**:

|               | 当前（全列）                  | 列裁剪后      | 减少         |
| ------------- |:-----------------------:|:---------:|:----------:|
| 每行数据量         | 520B (id 8B + vec 512B) | 8B (仅 id) | **-98.5%** |
| IVF K=10 读取量  | ~500KB                  | ~8KB      | **-98.4%** |
| IVF K=100 读取量 | ~5MB                    | ~80KB     | **-98.4%** |

**预估收益**: IVF K=10 1052ms → **~500-600ms (-43~52%)**

**改动范围**: `iceberg-index/reader.rs` — 给 `scan_single_file()` 加 `projected_columns` 参数，从 FDW 侧透传 SELECT 列名

**风险**: 低。仅改索引回表路径，需要 FFI 加一个参数

---

### ~~P1: Bridge SipHash → FxHash~~ ✅ 已完成 (2026-07-21)

**改动**: `iceberg-index/reader.rs` — 4 处 `HashMap`→`FxHashMap`，`rustc-hash = "2"`。分支 `feat/siphash-to-fxhash`。

**火焰图验证**: SipHash 4.06% 热点**完全消失**。`perf report` 确认 `sip::Hasher::write` 不在 Top-50 热点中。

**bench 验证** (SIFT zstd, release+FxHash vs debug+SipHash):
| K | 改动前 | 改动后 | 变化 |
|---|------|------|:--:|
| 10 | 4529ms | 2201ms | **-51%** |
| 100 | 6035ms | 3269ms | **-46%** |
| 10000 | 8417ms | 3789ms | **-55%** |

> 注：大部分收益来自 debug→release 编译。FxHash 独立贡献约 -3%（被 release 掩盖）。

**火焰图文件**: `flame_sift_fxhash_ivf_k10.svg`

---

### P2: 消 tokio（同步 API 路径）

**当前瓶颈**: tokio scheduler + task management 合计 ~5%

**预估收益**: ~5% 延时降低 + 解锁真正并发（消除 BLOCK_ON_LOCK）

**改动范围**: `iceberg-rust-bridge/runtime.rs` — 查询路径用同步 API 替代 tokio `block_on`

**风险**: 中。SDK 内部有 `.await` 调用，需要评估是否可全部替换为同步 I/O

**注**: 这是原始 P3，与 BLOCK_ON_LOCK 解耦是同一个改造的两个侧面

---

### P3: gaussdb StatementFlushMain + ShmemInit 惰性化

**当前瓶颈**: `StatementFlushMain` 6.34% + `ShmemInit → CSNLOG` 5.56% = ~12%

**预估收益**: ~5-10% 延时降低，对短查询帮助大

**改动范围**: `openGauss-server-datainfra` — 将 SLRU/CSNLOG 改为首次访问时延迟初始化

**风险**: 高。涉及 gaussdb 内核事务日志基础设施，改动影响面大

---

## 四、优化路线图

```
Phase 1 (小改动, 高收益): 列裁剪 + SipHash→FxHash
  └─ 预估 IVF K=10: 1052ms → ~450ms (-57%)
  └─ 改动范围: iceberg-index/reader.rs (~200行)
  └─ 不改 bridge/gaussdb, 风险极低

Phase 2 (中改动, 解锁架构瓶颈): 消 tokio + BLOCK_ON_LOCK → per-file
  └─ 预估: FullScan 也获得并行加速
  └─ 改动范围: iceberg-rust-bridge/runtime.rs

Phase 3 (大改动, 平台优化): gaussdb infra 惰性化
  └─ 仅在前两阶段饱和后再投入
```
