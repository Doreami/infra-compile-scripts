## 二、延迟对比

```
  K       fxhash 基线    sparse-row-take   差异
  ──────────────────────────────────────────────
  K=1       19,056          19,019        -0.2%
  K=10      19,975          18,467        -7.6%
  K=100     20,086          18,929        -5.8%
  K=1000    21,350          18,699       -12.4%
  K=10000   26,321          19,152       -27.2%
```

**稀疏 take 延迟几乎不随 K 增长**——K=1 到 K=10000 全在 ~19s。fxhash 延迟则随候选数量线性增长，K=10000 时差距扩大到 7 秒（-27.2%）。

## 三、K 值与 fetch_k

gaussdb 中 fetchK 计算（`planvectorsearch.cpp`）：

```
VECTORSEARCH_FETCH_MULTIPLIER = 5,  MIN = 50,  MAX = 10000
fetchK = max(min(topK × 5, 10000), max(topK, 50))
```

| SQL K | fetchK | fxhash | sparse | 说明 |
|:--:|:--:|:--:|:--:|------|
| 1 | 50 | 19,056 | 19,019 | 候选少，差异在噪声内 |
| 10 | 50 | 19,975 | 18,467 | -1.5s |
| 100 | 500 | 20,086 | 18,929 | 候选 10×，fxhash 开始涨 |
| 1000 | 5,000 | 21,350 | 18,699 | -2.7s，12% |
| 10000 | 10,000 | 26,321 | 19,152 | -7.2s，27% |

fxhash 延迟增长源自应用层物化：全文件解码后逐行匹配 HashMap → `take_record_batch`，候选越多开销越大。sparse 将行级过滤下沉到 Parquet decoder，候选数不影响延迟。

## 五、K 值越大收益越明显的原因

稀疏 take 将行级过滤从应用层下沉到 Parquet decoder 层：

**fxhash 路径**：`scan_single_file`（全文件解码）→ `read_single_file_rows_addressed`（逐行匹配位置）→ `materialize_candidates`（HashMap join + `take_record_batch`）。应用层物化开销 O(fetch_k)，候选越多越慢。

**sparse 路径**：`scan_single_file`（传入 `row_positions`）→ pipeline 内 `build_row_selection_from_row_offsets` → `RowSelection` → Parquet decoder 层精确选行。开销 O(文件数)，与候选数无关。

```
fxhash 延迟增长来源:
  K=10   (50候选):  19.2s = 文件I/O(18s) + 物化(1s)
  K=1000 (5000候选): 21.4s = 文件I/O(18s) + 物化(3s)  ← 物化涨了
  K=10000(10000候选): 26.3s = 文件I/O(18s) + 物化(8s)  ← 物化主导

sparse 延迟恒定:
  K=1~10000: ~19s = 文件I/O(18s) + RowSelection(<1s)  ← 物化被消除
```

其核心价值不是"让每次查询更快"，而是**让延迟不再随候选数量增长**——这对于高召回场景（大 K、高 refine_factor）至关重要。

## 八、结论

| 问题 | 回答 |
|------|------|
| 稀疏 take 是否有效？ | ✅ 有效。延迟不随 K 增长，K=10000 时 -27.2% |

## 九、后续代码优化方向

当前瓶颈已从应用层物化转到文件级固定开销（20 次 open + read metadata）。代码层可继续优化：

| 方向 | 描述 | 预期收益 |
|------|------|:--:|
| **文件级并行回表** | 当前 `scan_single_file` 对 20 个文件串行读取，可改为并行 | 中等 |
| **Parquet footer 缓存** | 连续查询间缓存 footer + page index，避免每次重新读取 | 低~中 |
| **消除 tokio** | bridge 用同步 I/O 替代 tokio `block_on`，减少调度开销 | 低 |
| **fetch_k 自适应** | 当前 MIN=50 在小 K 场景做无用功，可降低或按数据集调优 | 低 |

> 更大收益需从架构层面突破：减少候选命中文件数（数据按向量聚类分区）或让索引直接返回完整行数据（covering index）。
