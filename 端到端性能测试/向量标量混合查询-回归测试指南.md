# 向量+标量混合查询 · 回归测试指南

> 目的：把「向量+标量混合查询（物化路径优化）」的正确性与性能固化为**可重复执行、可手动操作的基准**。
> 用法：**改代码前跑一次、改后跑一次，比对结果**——任何延迟回归、结果变化、devtest 失败都能被发现。
> 覆盖：数据（MoReVec/SIFT/GIST）→ 正确性回归（devtest）→ 性能回归（MoReVec A/B）→ 结果比对。

---

## 0. 两个测试层次

| 层次 | 工具 | 验证什么 | 何时跑 |
|---|---|---|---|
| **正确性** | devtest 全套（serial_schedule） | 功能/结果正确、EXPLAIN 标注（Materialization） | 每次改代码后 |
| **性能** | `bench_morevec.py` | 端到端延迟（基线 vs 优化）+ 结果集一致性 | 每次改代码后（对比参考基线） |

> 正确性必须全绿才谈性能。性能比对看**相对变化**（本指南 §5 参考基线），绝对值受机器负载影响。

## 4. 性能回归（MoReVec A/B）

### 4.1 跑当前 build 基准

```bash
cd ~/infra-compile-scripts/端到端性能测试
python3 bench_morevec.py --table reviews --k 10,100 \
  --filters 0,1,2,3,4,5,6 --nqueries 30 --rounds 3 --dop 1 \
  --out /tmp/ab_now.json \
  --gsql ~/iceberg-og/openGauss-server-datainfra/mppdb_temp_install/bin/gsql
```

输出：每 (filter_id, K) 的 median/p99 延迟 + `result_ids_sample`（正确性用）。

### 4.2 切基线 build（对比历史代码）

```bash
# ① 三个仓 stash（#26-29 改动）→ 回到 HEAD 基线
for r in iceberg-index iceberg-rust-bridge iceberg_fdw; do (cd ~/iceberg-og/$r && git stash); done

# ② 编译部署
bash ~/infra-compile-scripts/build.sh bridge --release
bash ~/infra-compile-scripts/build.sh fdw --force --release   # fdw Makefile 无 header 依赖，必须 --force

# ③ 重启 gaussdb 使 .so 生效
kill $(pgrep -u $USER -x gaussdb) 2>/dev/null; sleep 3
ulimit -n 65536
nohup gaussdb -D ~/ogdata -p 37000 > ~/ogdata/server.log 2>&1 & sleep 5

# ④ 跑基线基准
python3 bench_morevec.py --table reviews --k 10,100 \
  --filters 0,1,2,3,4,5,6 --nqueries 30 --rounds 3 --dop 1 \
  --out /tmp/ab_baseline.json \
  --gsql ~/iceberg-og/openGauss-server-datainfra/mppdb_temp_install/bin/gsql

# ⑤ 恢复优化 build
for r in iceberg-index iceberg-rust-bridge iceberg_fdw; do (cd ~/iceberg-og/$r && git stash pop); done
bash ~/infra-compile-scripts/build.sh bridge --release
bash ~/infra-compile-scripts/build.sh fdw --force --release
kill $(pgrep -u $USER -x gaussdb) 2>/dev/null; sleep 3
nohup gaussdb -D ~/ogdata -p 37000 > ~/ogdata/server.log 2>&1 & sleep 5
```

> `git stash list` 确认 3 仓各一条 stash，避免误 pop。改代码对比时：`基线` = 改动前，`当前` = 改动后，不必真切到 HEAD。

### 4.3 比对

```bash
# 延迟：同 (filter,K) 比 median_ms（优化应显著低于基线，低选择性档最明显）
# 正确性：result_ids_sample 两 build 必须逐行一致
python3 - <<'EOF'
import json
a = json.load(open('/tmp/ab_now.json'))['results']
b = json.load(open('/tmp/ab_baseline.json'))['results']
print(f"{'label':28} {'now(ms)':>10} {'base(ms)':>10} {'加速比':>8}  结果一致")
for k in a:
    if k in b:
        same = a[k].get('result_ids_sample') == b[k].get('result_ids_sample')
        print(f"{k:28} {a[k]['median_ms']:>10.1f} {b[k]['median_ms']:>10.1f} "
              f"{b[k]['median_ms']/a[k]['median_ms'] if a[k]['median_ms'] else 0:>7.2f}x  {same}")
EOF
```

## 5. 参考基线（2026-08-26，A/B 实测：基线分支 vs 优化分支）

> MoReVec reviews，`bench_morevec.py`（10 查询 × 2 轮中位数，DOP=1）。
> 改代码后与本表对比：任何档位延迟明显上升（>10%）或结果集不一致 = 回归。

| tier | 基线(ms) | 优化(ms) | 差(ms) | 加速 |
|---|---|---|---|---|
| No K10 | 1672.5 | 1656.5 | 16.0 | 1.0% |
| No K100 | 1882.3 | 1873.7 | 8.6 | 0.5% |
| 1% K10 | 1667.6 | 1660.0 | 7.6 | 0.5% |
| 1% K100 | 1891.3 | 1869.5 | 21.8 | 1.2% |
| 50% K10 | 1675.0 | 1656.6 | 18.4 | 1.1% |
| 50% K100 | 1897.1 | 1874.9 | 22.3 | 1.2% |

movies 对照：No K1000 快 2.3%、50% K1000 快 1.6%。

### ⚠️ 重要实测结论（2026-08-26）

1. **物化优化（#26-29）延迟收益 ~0.5-1.2%**——设计文档"物化是最大耗时"的前提在实测下不成立：每查询的端到端延迟被固定 setup/索引加载成本主导（movies ~95ms / reviews ~1.8s），物化省下的几 ms 相对地板微乎其微。
2. **结果集两 build 一致**（正确性 OK；scalar-first 过滤精确，`Rows Removed by Filter` 与选择性吻合）。
3. **真正的性能瓶颈 = 每查询 setup/索引加载**（非物化）——修它能让所有向量查询快 20-100×，是比物化优化更大的机会（待定位：`load_view`/索引段加载为何每查询重复）。
4. 因此本指南的**性能回归**目前只能作为"无回归"守门（改代码后不得明显变慢、结果不得变化），不能作为"优化收益"证明。优化收益验证需先解决 #3 的 setup 成本。

## 6. 常见问题

| 现象 | 处理 |
|---|---|
| devtest FAIL | `cat test/results/regression.diff` 看差异；Materialization 标注变化 = FDW/引擎改动预期，需同步 expected |
| gaussdb 未运行 | `gaussdb -D ~/ogdata -p 37000 &` |
| fdw 编译报 GLIBCXX | `build.sh fdw` 自带清 LD_LIBRARY_PATH；手动 make 需 `LD_LIBRARY_PATH=` |
| 改了 fdw struct 但行为异常 | fdw Makefile 无 header 依赖，改 `include/iceberg_fdw.h` 后必须 `build.sh fdw --force --release` |
| 基准无计时 | 确认 gaussdb 运行 + 表/索引存在（`SELECT count(*) FROM more_ns.reviews`）|
