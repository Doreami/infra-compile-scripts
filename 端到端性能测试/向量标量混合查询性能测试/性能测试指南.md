# 向量+标量混合查询 性能测试指南

> **用途**：对「向量检索 + 标量过滤」混合查询做**性能测试与看护**——在任意当前代码上，按本指南即可完成数据准备、性能测试、结果查看与瓶颈定位。**与具体代码改动无关**。
> **场景**：`SELECT ... WHERE <标量条件> ORDER BY vec <-> q LIMIT K`（向量索引召回 + 标量过滤 + 内核精确重排）。

## 2. 数据准备

### 2.1 MoReVec（推荐：真实过滤负载）

MoReVec = 电影/评论文本 embedding 数据集（768 维），自带属性列（可标量过滤）与**过滤选择性定义**（真实过滤率档位）。数据获取见 §7。

```bash
cd <TEST_DIR>
python3 setup_morevec.py \
  --input <DATA_DIR>/MoReVec_small/datasets/reviews_dataset_0.hdf5 \
  --namespace more_ns --table reviews --num-clusters 512 --gsql <GSQL>
```

**`setup_morevec.py` 功能**：

- 读 MoRe HDF5：`train_rvector`（评论文本向量）或 `train_mvector`（电影），float64→float32；`train_*` 属性列（float64→double / bytes→string）。
- 建表（`id long + vec vector(768) + 属性列`）→ 写数据（pyiceberg）→ 建 IVF_PQ 索引。
- 自动把 metadata format-version 3→2（pyiceberg 兼容）。
- 小 chunk（5000 行/文件）写入：每 parquet 文件 1 个 ~16MB row-group。**回表读（按行号取行）性能关键在 row-group 大小**——若每文件一个巨 row-group（如 157MB），读几行也要解压整组，回表极慢（实测差 ~2×）。5000 行/文件是平衡点（文件数与 row-group 大小的折中）。

**数据集信息**（MoReVec_small）：

| 表       | 行数      | 维度  | 向量列   | 过滤列（selectivity 档）                      | 数据大小        |
| ------- | ------- | --- | ----- | --------------------------------------- | ----------- |
| reviews | 247,286 | 768 | `vec` | `total_votes`（1%/2%/5%/10%/20%/50%）     | ~1.4GB HDF5 |
| movies  | 9,999   | 768 | `vec` | `avgrating`（1.2%/2.3%/5.3%/11%/20%/51%） | ~58MB HDF5  |

> reviews 是主基准表（够大）；movies 仅 9999 行，适合正确性/快速验证，性能意义小。

**参数说明**：

| 参数                    | 必填  | 说明                                      |
| --------------------- | --- | --------------------------------------- |
| `--input`             | 是   | MoRe HDF5 路径（movies 或 reviews 数据集文件）    |
| `--namespace`         | 是   | 目标 schema 名（如 `more_ns`）                |
| `--table`             | 是   | 目标表名（如 `reviews`）                       |
| `--num-clusters`      | 是   | IVF 聚类数（reviews 约 512、movies 约 32，按数据量） |
| `--gsql`              | 是   | gsql 绝对路径                               |
| `--max-rows`          | 否   | 截取行数（大表先截段快速验证）                         |
| `--partition-buckets` | 否   | 建分区表（DOP 并行用，默认 0=不分区）                  |

导入后确认：

```bash
<GSQL> -d postgres -p <PORT> -t -A -c "SELECT count(*) FROM more_ns.reviews"   # 期望 247286
<GSQL> -d postgres -p <PORT> -t -A -c "SELECT index_status FROM iceberg_catalog.table_indexes WHERE namespace='more_ns' AND table_name='reviews'"  # active
```

### 2.2 SIFT/GIST + cat（备选：不同维度/规模）

```bash
cd ~/infra-compile-scripts/端到端性能测试
python3 setup_fixed.py --input 测试文件/sift_base.fvecs --namespace sift_ns --table sift1m_cat --partition-buckets 32 --cat-column
python3 setup_fixed.py --input 测试文件/gist-960-euclidean.hdf5 --namespace gist_ns --table gist1m_cat --partition-buckets 32 --cat-column
```

`--cat-column` 追加 `cat` 列：`cat = (id-1) % 10`，即给每行分配 0~9 十个值之一（取模均匀分配，**每个值恰好占全部行的 1/10**）→ 按 `cat` 过滤 = 精确控制过滤掉的比例（如 `cat='1'` 只留 10% 行）。

**SIFT/GIST 怎么测试**：`bench_morevec.py` 面向 MoReVec（读它的过滤定义/查询文件）。SIFT/GIST 用**手动 SQL** 测（同形状的查询，向量从表里取或官方 query 文件）：

```bash
# 取一个查询向量（如表内 id=1 的 vec）
QV=$(<GSQL> -d postgres -p <PORT> -t -A -c "SELECT vec FROM sift_ns.sift1m_cat WHERE id=1")

# 无过滤 / 各 cat 档位（cat='1' 留 10%、cat>='5' 留 50%）
<GSQL> -d postgres -p <PORT> -c "SET enable_vectorsearch=on; SET query_dop=1; \
  EXPLAIN ANALYZE SELECT id FROM sift_ns.sift1m_cat WHERE cat='5' ORDER BY vec <-> '$QV'::vector LIMIT 10;"
```

按 §3 的格式：每档位跑 3 轮取中位数。SIFT 128 维 / GIST 960 维，可对比不同维度下物化优化的收益差异（GIST 向量列更宽，物化收益应更大）。

## 3. 启动性能测试

### 3.1 单次性能测试（只测当前代码，不对比）

```bash
cd <TEST_DIR>
python3 bench_morevec.py \
  --table reviews \                    # 表名：movies 或 reviews
  --k 10,100 \                         # K 档位（LIMIT），逗号分隔
  --filters 0,1,3,5,6 \                # 过滤档位 id（0=无过滤对照，1-6=选择性档）
  --nqueries 20 \                      # 每档取前 N 条查询
  --rounds 3 \                         # 每查询计时轮数（取中位数）
  --dop 1 \                            # query_dop
  --out /tmp/bench.json \              # 结果输出路径
  --gsql <GSQL> \
  --port <PORT> \
  --namespace more_ns                  # 默认已是 more_ns
```

**`bench_morevec.py` 功能**：从 MoRe 过滤定义 + 每过滤档的查询向量（HDF5）生成 SQL → 批量 `EXPLAIN ANALYZE` 执行 → 计时（`Total runtime` 中位数）→ 存结果集。**默认查 `<namespace>.<table>`**（如 `more_ns.reviews`）。

**参数说明**：

| 参数            | 默认              | 说明                                                                             |
| ------------- | --------------- | ------------------------------------------------------------------------------ |
| `--table`     | 必填              | `movies` 或 `reviews`（决定用哪张表 + 哪个过滤定义/查询文件）                                     |
| `--namespace` | `more_ns`       | 表所在 schema                                                                     |
| `--k`         | `10,100`        | K 档位列表，逗号分隔                                                                    |
| `--filters`   | `0,1,2,3,4,5,6` | 过滤档位 id（0=无过滤）。过滤串从 `filters/{type}_filters_0.hdf5` 取，如 `total_votes >= 743.0` |
| `--nqueries`  | `30`            | 每档查询条数（MoRe 每档有 1000 条可用；越多越稳但越慢）                                              |
| `--rounds`    | `3`             | 每查询计时轮数，取中位数抗波动                                                                |
| `--dop`       | `1`             | query_dop（分区表可 >1）                                                             |
| `--out`       | 无               | 结果 JSON 路径                                                                     |
| `--gsql`      | 必填              | gsql 绝对路径                                                                      |
| `--port`      | `37000`         | gaussdb 端口                                                                     |

**输出 JSON**：每 (filter, K) 一个条目：`median_ms / p99_ms / mean_ms / result_ids_sample`（结果集，正确性/一致性用）。

**示例**：

```bash
# 完整档位（1%/5%/20%/50% 选择性 + 无过滤）
python3 bench_morevec.py --table reviews --k 10,100 --filters 0,1,3,5,6 --nqueries 20 --rounds 3 --out /tmp/bench.json --gsql <GSQL>

# 快速冒烟（验证流程通）
python3 bench_morevec.py --table reviews --k 10 --filters 0,1 --nqueries 5 --rounds 1 --out /tmp/bench_smoke.json --gsql <GSQL>
```

> 提示：`EXPLAIN ANALYZE` 的 `Total runtime` = 服务端整条 SQL 执行时间（含 FDW/bridge 扫描初始化）。

### 3.2 两个构建对比（可选，性能看护用）

```bash
# 构建 A 跑一次
python3 bench_morevec.py --table reviews --k 10,100 --filters 0,1,3,5,6 --nqueries 20 --rounds 3 --out /tmp/build_a.json --gsql <GSQL>
# 构建 B（如改代码后）跑同一条
python3 bench_morevec.py --table reviews --k 10,100 --filters 0,1,3,5,6 --nqueries 20 --rounds 3 --out /tmp/build_b.json --gsql <GSQL>
# 对比
python3 ab_compare.py /tmp/build_a.json /tmp/build_b.json
```

`ab_compare.py` 逐 (filter, K) 输出「A median / B median / 差(ms) / 加速% / 结果集是否一致」。延迟明显变慢（>10%）或结果集不一致 = 回归。

### 3.3 并行（DOP）测试

**前提**：DOP>1 需要**分区表**（非分区表 DOP>1 不生效）。导入时加 `--partition-buckets 32`（如 `setup_morevec.py ... --partition-buckets 32`）。

```bash
# 同一条 SQL，跑不同 DOP（1/2/4/8；>8 会被内核截断为 8）
python3 bench_morevec.py --table reviews --k 10,100 --filters 0,1,3,5,6 \
  --nqueries 20 --rounds 3 --dop 1,2,4,8 --out /tmp/bench_dop.json --gsql <GSQL>
```

`--dop` 支持逗号分隔多值，输出按 `dop` 分档。观察：延迟随 DOP 是否下降（并行扩展性）、P99 抖动。

## 4. 查看测试结果

```bash
# 直接看 JSON
python3 -c "import json; d=json.load(open('/tmp/bench.json')); [print(k, v['median_ms'], v['result_ids_sample']) for k,v in d['results'].items()]"
```

结果解读：

- `median_ms` = 端到端延迟（越小越好）；`p99_ms` = 抖动。
- 不同过滤档对比：高选择性（低存活率）档通常应比无过滤快（物化成本随存活行减少）；若各档几乎一样，说明成本不在物化（用 §5 定位）。

## 5. 火焰图分析瓶颈

```bash
bash flame_morevec.sh /tmp/flame_out "total_votes >= 743.0" [gaussdb_pid]
```

功能：取一个 MoRe 查询向量 → 生成查询 SQL → `perf` 采样期间连续跑 10 次 → 生成 `flame.svg`（火焰图）+ `report.txt`（顶层热点）。

- 第三参数显式传 gaussdb PID；缺省自动找「命令行含 `-p <PORT>`」的 gaussdb（排除 devtest 临时实例）。

**环境坑**：perf 前必须 `export LD_LIBRARY_PATH=`（opengauss 旧 lib 让 perf 报 "Access to performance monitoring limited"）；但 gsql 需要 LD_LIBRARY_PATH（GAUSSHOME lib）——脚本内 perf 用清空环境，gsql 用正常环境。

**解读**：

- 火焰图 gaussdb 分支最宽栈 = CPU 热点。

- **gaussdb 线程 CPU 占比极低** = 瓶颈是等待（I/O/锁/阻塞），不是 CPU。此时查：parquet row-group 大小（§2.1，大 row-group → 回表读慢）、索引加载、锁竞争。

- 手动 perf 备用：
  
  ```bash
  export LD_LIBRARY_PATH=
  perf record -a -F 99 -g -o /tmp/perf.data -- sleep 10 &   # 期间跑查询
  perf script -i /tmp/perf.data | ~/FlameGraph/stackcollapse-perf.pl | ~/FlameGraph/flamegraph.pl > /tmp/flame.svg
  ```

### 7.1 数据集获取（MoReVec）

- **数据**：MoReVec 在 Google Drive（[文件夹链接](https://drive.google.com/drive/folders/1AqAVI8ASROqrFCQdEMPB8RNzPwilijRp)）。国内网络直连通常不通，有代理时可下载：
  
  ```bash
  python3 -c "import gdown; gdown.download_folder(url='https://drive.google.com/drive/folders/1AqAVI8ASROqrFCQdEMPB8RNzPwilijRp', output='morevec_small')"
  # 小数据集 ~1.6GB；再 scp 到 <DATA_DIR>/MoReVec_small/
  ```

- **来源项目**：[aabylay/ANN-benchmark-HQ](https://github.com/aabylay/ANN-benchmark-HQ)（过滤向量检索基准，论文 [arXiv:2602.11443](https://arxiv.org/abs/2602.11443)）。

- **数据集结构**：`datasets/{movies,reviews}_dataset_0.hdf5`（向量+属性）、`filters/*_filters_0.hdf5`（过滤串 + selectivity）、`queries/queries_flex_{type}_sim_0_{filter_id}.hdf5`（每过滤档 1000 查询 + GT）。

### 7.2 更大的数据集（MoReVec medium / large）

MoReVec 分 `small / medium / large` 三档（同 Google Drive 文件夹，`load_morevec.py` 或 gdown 下载全量）。用更大档位时注意：

1. **下载**：gdown 下载整个文件夹（含 small/medium/large），`morevec_small` 子目录即小档。medium/large 更大（GB 级），确认磁盘空间（服务器 `/data` 充足）。
2. **导入**：`setup_morevec.py --max-rows <N>` 可先截段快速验证；完整导入耗时长（读 HDF5 + 写 + 建索引，大档可能数十分钟），用 `--num-clusters` 按数据量调大（如 large 用 1024+）。
3. **索引构建**：`create_index` 同步调用对大数据可能超 600s（脚本内 gsql timeout）。建议**异步建索引**：
   
   ```bash
   <GSQL> -d postgres -p <PORT> -c "SELECT iceberg_catalog.create_index('more_ns','reviews','idx_ivf_pq_vec','[\"vec\"]'::jsonb,'ivf_pq','ivf','{\"vector_column\":\"vec\",\"num_clusters\":1024,\"sample_rate\":100000}'::jsonb, p_is_async => true, p_num_workers => 8);"
   <GSQL> -d postgres -p <PORT> -t -A -c "SELECT index_status FROM iceberg_catalog.table_indexes WHERE namespace='more_ns' AND table_name='reviews'"  # 轮询到 active
   ```
4. **性能看护注意**：
   
   - 更大数据集 → 索引加载/搜索成本上升（索引段更大）。
   
   - `bench_morevec.py --nqueries` 调小（每查询更慢），`--rounds` 保持 2-3。
   
   - 分区表（`--partition-buckets`）支持 DOP 并行。
   
   - 查询向量仍用每档的 `queries_flex_*` 文件（档位结构一致）。

### 7.3 常见问题

| 现象                               | 处理                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------- |
| `Materialization` 是 EXPLAIN 里的什么 | FDW 对向量路径的物化方式标注：`scalar-first`（先标量过滤再读向量列）/ `projection-only`（无过滤，只读输出列+向量列） |
| 查询很慢且各过滤档都差不多                    | 回表读 row-group 大（§2.1 小 row-group 可缓解）或索引加载成本高                                 |
| perf 报 Access limited            | `export LD_LIBRARY_PATH=`（opengauss 旧 lib 污染）                                 |
| devtest/功能测试                     | 见回归测试指南（正确性），本指南只做性能                                                          |
