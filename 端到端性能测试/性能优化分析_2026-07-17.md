## 背景：火焰图数据摘要

基于 SIFT1M 火焰图（2026-07-16），当前 IVF 向量索引 K=10 查询的 CPU 热点分布：

```
Parquet 解码          ████████ 35-37%    <- RLE 14% + ListArray 13% + Rep/Def ~12%
内核 [unknown]        ██████ 10-18%      <- 缺页/内存拷贝
tokio 异步运行时      ████ ~10%          <- bridge_block_on
Parquet 底层工具      ███ 3-7%           <- Zstd/Huffman
gaussdb 基础设施      ██ ~5%             <- 锁/缓存
向量索引搜索          ▏ <1%              <- 已经极致优化
```

**核心结论**：索引搜索本身 CPU 开销 <1%（已最优），瓶颈全在 **Parquet 数据解码管道**（35%+）。

### GIST1M 验证（960维，2026-07-17）

高维场景进一步验证了瓶颈定位：

```
SIFT (128维)            GIST (960维)
IVF:    1.0s            IVF:    19.9s
全扫:   2.4s            全扫:   21.0s
加速比: 2.3×            加速比: 1.03×  ← 几乎消失！

内核占比: ~10%          内核占比: ~26%  ← 增长 2.6×
Parquet解码: ~35%       Parquet解码: ~15% ← 被内核稀释
```

**维度越高，内存带宽越成为瓶颈**。960 维时内核缺页从 10%→26%，IVF 减少扫描行的收益被内核开销完全稀释。这意味着 **P0/P1 优化（列裁剪、fixed 类型）在高维场景收益更大**——减少 I/O 直接降低缺页。同时**P3（消 tokio）在高维场景优先级降低**（tokio 相对占比从 10%→3%）。

### 1.1 类型映射：`vector -> list<float>` 硬编码 [FDW 侧]

**位置**: `type_adapter.cpp:71-73` (commit `d9631c5`)

```cpp
case VECTOROID:
    (void)icebergVectorDimFromTypmod(pg_typmod, attname);
    mapping->iceberg_type = pstrdup("list<float>");  // <- 硬编码
    break;
```

**问题**: `vector(n)` 是定长类型，但 FDW 总是映射为 `list<float>`（嵌套类型）。Iceberg 本身支持 `fixed(n)` 定长原始类型，不需要 Rep/Def Level 编码。

**优化方案**:

```cpp
case VECTOROID: {
    int dim = icebergVectorDimFromTypmod(pg_typmod, attname);
    // 新增 fixed(n) 映射路径
    // 条件：bridge 支持 fixed 类型读取 + Iceberg 表 schema 匹配
    mapping->iceberg_type = pstrdup("list<float>"); // 保持现状；fixed 支持需协调改
    mapping->vector_dim = dim;  // 新增字段，供建表时选择 fixed vs list
    break;
}
```

**预估收益**: 消除 Rep/Def Level (12%) + ListArrayReader (13%) = **~25% CPU**，IVF K=10 从 1044ms -> 预期 ~780ms。

**依赖**: 需要 Iceberg 表 schema 改为 `fixed(128)` + bridge Parquet reader 支持 fixed 类型直接读取。

**风险**: FDW、Catalog、Bridge 三方同时改造，协调成本高。

### 1.2 逐行物化 vs 批量物化 [FDW 侧]

**位置**: `iceberg_fdw.cpp:1874-1882` (`icebergIterateForeignScan`) + `sdk_scan_adapter.cpp:580-590` (`iceberg_sdk_scan_materialize_row`) (commit `d9631c5`)

当前逐行循环：

```cpp
// iceberg_fdw.cpp:1874-1882 (commit d9631c5)
for (;;) {
    if (iceberg_sdk_scan_next(state->sdk_scan, NULL, NULL) > 0) {
        if (iceberg_sdk_scan_materialize_row(state->sdk_scan, slot)) {
            return slot;  // <- 每次只返回一行给 openGauss
        }
    }
}
```

`sdk_scan_adapter.cpp` 中已经实现了 batch 内缓存机制：

```cpp
// sdk_scan_adapter.cpp:509-518 (commit d9631c5)
while (!scan->has_current_batch || scan->current_row >= scan->current_batch.length) {
    if (!icebergSdkScanLoadNextBatch(scan)) {
        return 0;
    }
}
```

```cpp
// sdk_scan_adapter.cpp:580-589 (commit d9631c5)
bool iceberg_sdk_scan_materialize_row(IcebergSdkScan *scan, TupleTableSlot *slot) {
    int64 row = scan->current_row++;
    return iceberg_arrow_materialize_projection_row(
        &scan->current_batch, row, scan->request.projected_columns, slot);
}
```

**评估**: 当前 `IcebergSdkScan` 已经缓存 Arrow batch (`current_batch`) 并逐行索引 (`current_row`)。openGauss 的 `ExecScan` 每次调用 `IterateForeignScan` 只拿一行。对 hybrid task_group 路径，Arrow batch 已在 C 侧内存中，每次 `materialize_row` 走 `icebergArrowColumnDatum` 逐列转换（含 `vector` 类型的 `InitVector + memcpy`）。

**优化方案**: 对不包含 vector 列的查询（纯属性列），可进一步把 batch 内多行的基础类型（int/float/text）直接批量构造 TupleTableSlot 数组。对含 vector 列的查询，当前逐行 `memcpy` 已接近最优。

**预估收益**: 对非向量列查询 ~2-3%，对含向量列查询已接近最优。**优先级下调至 P4。**

### 1.3 JSON 在 C 侧手写拼接 [FDW 侧]

**位置**: `index_scan_adapter.cpp:143-157` (`icebergIdxBuildNamespaceJson`) (commit `d9631c5`)

```cpp

{
    initStringInfo(&buf);
    appendStringInfoChar(&buf, '[');
    escape_json(&buf, namespace_name);  // <- 每次手写 JSON
```

**问题**: 简单字符串 `["sift_ns"]` 每次调 bridge 都要重新拼接+escape。同时 `icebergIdxFindIndexNameByKind`（`index_scan_adapter.cpp:292-333`）在 C 侧手工解析 JSON（`strstr` 遍历），容易出错且不可维护。

**预估收益**: <1%（非热点），但降低代码复杂度。

### 2.1 scan_single_file 全列读取（缺少列裁剪）[Bridge-索引侧]

**位置**: `reader.rs:309-320` (commit `9d4207e`)

```rust
async fn scan_single_file(&self, file_path: &str) -> Result<IndexBatchStream> {
    // [WA] 收集所有列名 -> 读全列
    let column_names: Vec<String> = self
        .table.metadata().current_schema().as_struct().fields()
        .iter().map(|f| f.name.clone()).collect();

    let scan = self.table.scan()
        .snapshot_id(self.snapshot_id)
        .select(column_names)  // <- 包含 vec 列！
        .build()?;
```

**问题**: 对 `SELECT id FROM ... ORDER BY vec <-> ... LIMIT 10`，只需要 `id` 列，但实际上 `vec` 列（128x4=512B/行）也被读取和解码了。对于 IVF K=10（~976 行），这意味着额外解码 ~500KB 的 float 数据。

**优化方案**: 将 projected columns 传入 `scan_single_file`：

```rust
async fn scan_single_file(
    &self, file_path: &str, projected_columns: &[String]
) -> Result<IndexBatchStream> {
    let scan = self.table.scan()
        .snapshot_id(self.snapshot_id)
        .select(projected_columns.to_vec())  // <- 只读需要的列
        .build()?;
```

**预估收益**: 减少 ~30% Parquet 解码量（跳过 vec 列），IVF K=10 预期 ~730ms。

**依赖**: 需要从 FDW 侧把 `projected_columns` 传过 FFI 到 `materialize_candidates` -> `scan_single_file`。

### 2.2 Puffin 索引文件懒加载（已部分实现）[Bridge-索引侧]

**位置**: `ivf.rs:914-979` (`IvfPlugin::load`) (commit `9d4207e`)

当前 IVF 加载策略（三阶段）：

```
Phase 1: read header (32 bytes) -> 解析 dimension/num_partitions
Phase 1: read centroids (K x dim x 4 bytes) -> 全部加载
Phase 1: read footer -> 解析 partition_offsets/sizes
Phase 2: load_partition(pid) -> 按需范围读 + LRU 缓存
```

**评估**: 当前设计已经比较优化。Header+centroids+footer 是轻量级的（nc=1024, dim=128 -> centroids = 1024x128x4 = 512KB）。真正的 502MB 是 partition data，已通过 LRU partition cache 延迟加载。**不需要额外优化。**

### 3.1 异步运行时开销（tokio current-thread + global mutex）[Bridge-公共侧]

**位置**: `runtime.rs:7-42` (commit `23aa21e`)

```rust
static RUNTIME: OnceLock<Runtime> = OnceLock::new();        // 单线程 tokio
static BLOCK_ON_LOCK: Mutex<()> = Mutex::new(());            // 全局互斥锁

pub fn bridge_block_on<F>(future: F) -> F::Output {
    let _guard = BLOCK_ON_LOCK.lock().unwrap();              // <- 串行化所有调用
    bridge_runtime().block_on(future)
}
```

**问题**:
1. 所有 C ABI 调用被 `BLOCK_ON_LOCK` 全局互斥锁串行化 -- 多查询并发完全被阻塞
2. tokio `block_on` 本身有调度开销（创建/销毁 ephemeral task）
3. 火焰图中 tokio 相关占比约 10%

**优化方案**:

```rust
// 方案 A: 多线程运行时（需确认所有 SDK 组件是 Send 的）
tokio::runtime::Builder::new_multi_thread()
    .worker_threads(4)
    .enable_all()
    .build()

// 方案 B: 同步 API 路径（推荐，最大收益）
// 对查询路径，提供不需要 tokio 的同步版本：
pub fn bridge_sync_read<F>(f: F) -> F::Output
where F: FnOnce() -> F::Output {
    f()  // 直接在当前线程执行，绕过 tokio
}
```

**预估收益**: 消除 ~10% tokio 开销，同时提升并发能力。

**风险**:
- 方案 A: 部分 SDK 组件可能不是 `Send`
- 方案 B: SDK 内部所有 `.await` 需要替换为同步调用，改动量大

```rust
    Ok((ffi_array, _ffi_schema)) => {
        ptr::write(out_batch as *mut FFI_ArrowArray, ffi_array);
        *out_is_last = batch.is_last;
    }
}
```

**评估**: Arrow C Data Interface 的 `to_ffi` 是零拷贝的（传递内部 buffer 指针）。C++ 侧 `iceberg_sdk_scan_materialize_row` 直接读取 Arrow 数组指针。**当前实现已是最优，无需额外优化。**

### 3.4 IndexEngine 单例用 Mutex [Bridge-公共侧]

**位置**: `metadata_abi.rs:37` (commit `23aa21e`)

```rust
static ENGINE: Mutex<Option<Arc<IndexEngine>>> = Mutex::new(None);
```

```rust
// metadata_abi.rs:39-54 (commit 23aa21e)
pub(crate) fn get_or_init_engine() -> Result<Arc<IndexEngine>, String> {
    let mut guard = ENGINE
        .lock()
        .map_err(|_| "engine mutex poisoned".to_string())?;
    if let Some(engine) = guard.as_ref() {
        return Ok(Arc::clone(engine));
    }
    let engine = IndexEngine::open(&OpenOptions { ... })
        .map_err(|e| format!("failed to init index engine: {e}"))?;
    *guard = Some(Arc::clone(&engine));
    Ok(engine)
}
```

**问题**: 每次 `get_or_init_engine()` 取锁，即使 engine 已初始化（常态）。这个函数在 `search_vector_by_metadata`、`build_index_by_metadata`、`drop_index_by_metadata` 等所有 index ABI 入口都被调用。

**优化方案**:

```rust
use std::sync::OnceLock;
static ENGINE: OnceLock<Arc<IndexEngine>> = OnceLock::new();

pub(crate) fn get_or_init_engine() -> Result<Arc<IndexEngine>, String> {
    ENGINE.get_or_try_init(|| {
        IndexEngine::open(&OpenOptions { ... })
            .map_err(|e| format!("failed to init index engine: {e}"))
    }).map(Arc::clone)
}
```

**预估收益**: 消除每次查询的 Mutex::lock 开销（~50ns -> 0），对短查询（btree 点查 171ms）帮助最大。

### 3.5 Parquet 编码选择（RLE vs PLAIN）[Bridge-公共侧]

**位置**: 写入侧（不在当前 `code/` 目录中，在 datainfra 的写入管线）

Parquet 的 RLE/Bit-Packing 编码是造成火焰图中 RleDecoder 14% 开销的根源。如果改为 PLAIN 编码：
- 消除 RLE 解码开销（14%）
- 代价是存储空间增大（RLE 对重复值高效的场景，PLAIN 会增大）

**评估**: 写入侧改变编码策略。对 `list<float>` 列（向量数据），RLE 作用于 Rep/Def Level 而非实际 float 值（float 值自身走 PLAIN 或 BYTE_STREAM_SPLIT）。改为 `fixed(128)` 类型后 Rep/Def 完全消除，RLE 开销自然消失。

## 四、修改方案详述

### 4.1 P0: `vector -> fixed(n)` 类型映射（消除 25% 解码开销）

**类型**: FDW 侧 + Bridge-公共侧 + 写入侧（三方协调）

**问题火焰图关联**: RLE 14% + Rep/Def 12% + ListArrayReader 13% = 39%（上限），保守估计消除 ~25%

#### 当前流程

```
写入侧（datainfra）:
  vector(128) -> Iceberg schema: list<float> (嵌套类型)
    └─ Parquet 编码:
         ├─ Repetition Level: 每行 1 byte (RLE 编码)
         ├─ Definition Level: 每行 1 byte (RLE 编码)
         └─ 实际浮点值: PLAIN (4 bytes x 128 floats = 512 bytes)

读取侧（bridge -> FDW）:
  ArrowReaderBuilder.read()
    └─ ParquetRecordBatchStream
         ├─ RleDecoder::get_batch_with_dict     -> Rep/Def Level 解码 (~12% CPU)
         └─ ListArrayReader::consume_batch      -> 构造 ListArray 偏移量  (~13% CPU)
              └─ Arrow 导出: ListArray { offsets, values: Float32Array }
                   └─ FDW icebergArrowVectorDatum:
                        offsets[start]..offsets[end] -> dim
                        memcpy(values + offset, vec->x, dim * 4)
```

#### 优化后流程

```
写入侧（datainfra，需改造）:
  vector(128) -> Iceberg schema: fixed(128) (定长原始类型)
    └─ Parquet 编码:
         └─ 实际浮点值: PLAIN (4 bytes x 128 floats = 512 bytes)
         （无 Rep/Def Level！）

读取侧（bridge -> FDW，需适配）:
  ArrowReaderBuilder.read()
    └─ ParquetRecordBatchStream
         └─ 直接读取 FixedSizeBinary column （无 RLE，无 ListArrayReader）
              └─ Arrow 导出: FixedSizeList(128, Float32)
                   └─ FDW: 直接 memcpy(128 * 4) 无需解析 offsets
```

#### ASCII 流程图对比

```
当前路径（list<float>）:
┌──────────┐    ┌──────────┐    ┌───────────┐    ┌──────────┐    ┌──────────┐
│ Parquet  │ -> │ RleDec   │ -> │ Rep/Def   │ -> │ ListArr  │ -> │ Arrow    │
│ Page     │    │ 14% CPU  │    │ 12% CPU   │    │ 13% CPU  │    │ Export   │
└──────────┘    └──────────┘    └───────────┘    └──────────┘    └──────────┘
                                                       |
                                                FDW: offsets[start..end]
                                                     memcpy 512B -> vector varlena

优化后路径（fixed(128)）:
┌──────────┐                                       ┌──────────┐    ┌──────────┐
│ Parquet  │  ==================================>  │ Arrow    │ -> │ FDW      │
│ Page     │        跳过 Rep/Def/RLE/ListArray     │ Export   │    │ memcpy   │
└──────────┘                                       └──────────┘    └──────────┘
                                                        |
                                                 FixedSizeList(128, Float32)
                                                 直接 memcpy 无需解析 offset
```

#### 具体修改

**涉及文件**（按改动顺序）：

1. **写入侧**（datainfra，commit `c5adf7b6`）:
   - 建表时: 当列类型为 `vector(n)`，Iceberg schema 写为 `fixed(n * 4)` 而非 `list<float>`
   - 数据写入: 使用 Parquet `FixedLenByteArray` 物理类型，n*4 bytes per value
   - 写入侧不生成 Repetition/Definition Level

2. **FDW 侧** `type_adapter.cpp:71-73` (commit `d9631c5`):
   - `case VECTOROID`: `mapping->iceberg_type` 改为 `pstrdup("fixed")`（或保持 list<float> 并靠 catalog 侧映射）
   - 新增 `mapping->vector_dim = dim` 字段

3. **Bridge-公共侧** (commit `23aa21e`):
   - Parquet reader 对 `fixed(n)` 列的处理: Arrow C Data Interface 导出为 `FixedSizeList(n/4, Float32)` 或 `FixedSizeBinary(n)`
   - scan.rs 的 projection 构建需识别 fixed 类型列

4. **FDW 侧** `sdk_scan_adapter.cpp:269-313` (commit `d9631c5`):
   - `icebergArrowVectorDatum`: 对 `FixedSizeList` 类型，直接从 child[0] buffer 读取 fixed 长度，无需 offsets 数组解析

5. **Catalog**（openGauss-Catalog，commit `44e44dc`）:
   - `iceberg_catalog_get_table_info` 需返回列的类型信息，标记 vector 列为 fixed 还是 list

#### 预估收益

| 指标 | 当前 | P0 后 | 降低 |

| 全扫 K=10 latency | 2416ms | ~1810ms | **-25%** |
| Rep/Def Level 解码 | 12% CPU | 0% | 消除 |

| ListArrayReader | 13% CPU | 0% | 消除 |

- **三方协调**: FDW、Catalog、datainfra（写入）必须同时改造
- **兼容性**: 存量 `list<float>` 表需要迁移或双读路径

### 4.3 P2: Engine 单例 OnceLock（消除不必要的锁竞争）

**类型**: Bridge-公共侧

#### 当前流程

```
每次 index ABI 调用:
  search_vector_by_metadata()
    └─ get_or_init_engine()
         └─ ENGINE.lock()              // Mutex::lock，~50ns
```

```
每次 index ABI 调用:
```

**文件**: `metadata_abi.rs:33-54` (commit `23aa21e`)

#### 预估收益

- 消除每次调用 Mutex::lock（~50ns -> ~0ns）
- 对 btree 短查询（171ms）帮助最大
- 消除 `Mutex::lock` 可能触发的 OS futex 等待（高并发下）

### 4.4 P3: 同步 API 路径（消除 tokio 10% 开销）

**类型**: Bridge-公共侧

#### 当前流程

```
每个 C ABI 调用:
  ffi_boundary(body)
    └─ body():
         └─ bridge_block_on(async { ... })
              ├─ BLOCK_ON_LOCK.lock()      // 全局互斥
              └─ Runtime::block_on(future)
                   ├─ 创建 ephemeral task
                   ├─ poll future (SDK I/O)
                   └─ 销毁 task
```

#### 优化后流程（方案 B: 同步路径）

```
每个 C ABI 调用:
  ffi_boundary(body)
    └─ body():
         └─ bridge_sync_read(|| { ... })   // 直接在当前线程执行
              └─ 直接调用 SDK 同步方法
              （无 tokio, 无 mutex, 无 task 创建/销毁）
```

#### 具体修改

**文件**: `runtime.rs:7-42` (commit `23aa21e`)

对于查询路径（search_vector, 扫描），SDK 内部 I/O 调用可替换为同步版本：

1. 新增 `bridge_sync_read` 函数
2. 评估 SDK 内部哪些 `.await` 可以替换为 `std::thread::block_on` 或同步 I/O
3. 逐步迁移：先迁移热路径（扫描、search_vector），后迁移冷路径（建索引）

#### 预估收益

- 消除 tokio 调度 ~10% CPU
- 消除 BLOCK_ON_LOCK 全局互斥，提升并发
