## 三、核心发现：FullScan 快于 IVF（2.3-3.5×）

这是本次测试最重要的发现——**GIST 上 IVF 索引是负优化**：

| 场景 | 耗时 | vs 最快 |
|------|------|:--:|
| **None FullScan K=10** | **5,585ms** | ⭐ 最快 |
| None FullScan K=100 | 5,610ms | +0.4% |
| Zstd FullScan K=10 | 11,071ms | +98% |
| None IVF K=10 | 19,764ms | +254% |
| Zstd IVF K=10 | 25,463ms | +356% |

**IVF 无K值敏感性**：IVF K=10/100/10000 耗时几乎相同（~19.8-26.3s），说明瓶颈不在 Top-K 排序，而在索引扫描本身读取了过多数据。

## 四、火焰图根因分析

### 4.1 FullScan 热点（无压缩，5.6s）

```
kernel [unknown] (I/O)     ██████████████████████████████ 55.94%
  ├─ opendal BufferStream  ████████████████████████ 23.80%  ← 文件读取
  └─ tokio I/O poll        ████████████████ 16.50%
其他                        ██████████████████████ 44.06%
```

**FullScan 是 I/O bound**——55.94% 在内核态文件 I/O。3.6GB 顺序读取，瓶颈在磁盘/文件系统。

### 4.2 IVF 热点（无压缩，19.8s）

```
kernel [unknown]           ██████████████████████████ 45.81%
  ├─ GenericColumnReader   █████████████████ 33.28%  ← Parquet 列解码
  │   └─ FixedLenByteArrayReader                    ← fixed(3840) 读取
  │       └─ materialize_candidates                  ← 候选行回表
  └─ 其他 kernel
其他                        ██████████████████████████ 54.19%
```

**IVF 是 CPU bound**——33.28% 在 `GenericColumnReader::read_records`（Parquet 列解码）。因为 IVF 通过 `materialize_candidates` 做随机行读取，每次都要完整解码 Parquet 页面。

### 4.3 两种路径的调用栈对比

```
FullScan (快, I/O bound):               IVF (慢, CPU bound):
━━━━━━━━━━━━━━━━━━━━━━━━━━              ━━━━━━━━━━━━━━━━━━━━━━━━
opendal::BufferStream                    iceberg_index::reader
  └─ tokio I/O poll                        └─ materialize_candidates
       └─ FileRead::read                        └─ read_file_rows_addressed
            └─ [kernel 缺页]                          └─ scan_single_file (全列!)
                                                            └─ GenericColumnReader
                                                                 └─ FixedLenByteArrayReader
                                                                      └─ [kernel 缺页]
```

**IVF 慢的根因**：`scan_single_file` 读**全列**（vec 3840B/行），且通过 `materialize_candidates` 做随机行读取。即使只需 10 行结果，也要解码包含这 10 行的所有 Parquet 页面。

## 五、压缩效果对比

### FullScan：消除 Zstd 收益 50%

GIST FullScan 读 3.6GB 数据，Zstd 解压 3.1GB 的 CPU 开销巨大：
- SIFT FullScan（500MB→147MB）：zstd→none 改善仅 2%（I/O 小，解压占比低）
- **GIST FullScan（3.6GB→3.1GB）：zstd→none 改善 50%**（I/O 大，解压绝对开销高）

### IVF：消除 Zstd 收益 22%

IVF 的瓶颈在随机 Parquet 页面解码（33% CPU），Zstd 解压只是其中一部分。消除后剩余的 Parquet 解码仍是瓶颈。

## 七、SELECT id vs SELECT * — 列裁剪不可行

实测对比（无压缩 IVF K=10）：

| SELECT | 耗时 | Projection Columns |
|------|------|------|
| `SELECT id` | 19,756ms | **id,vec** |
| `SELECT *`  | 19,845ms | **id,vec** |

**`SELECT id` 和 `SELECT *` 耗时完全相同**。

### 列裁剪为何不可行——三层设计约束

1. **gaussdb VectorSearch 需要 vec**：IVFPQ 返回的是 PQ 近似距离，gaussdb 的 `VectorSearch` 节点用 `vec` 做精确 L2 重排序（`Distance Computations: 50`）。**vec 列不能跳过**。

2. **FDW 设计：索引路径 projection = 整表全列**：设计文档 `iceberg-fdw-design.md:118` 明确记录——"索引路径 `projected_columns` = 整表全列，bridge 输出「整表列 + `_distance`」"。这是刻意为之，为的是统一数据面。

3. **Bridge 设计：`scan_single_file` 始终读全列**：`reader.rs:309-312` 写死——"Collect all column names from the current schema so we read the full row (back-to-table use case)"。projected_columns 传不下来。

**结论：列裁剪在当前架构下被三层设计约束封堵，不是快速优化项。**

## 八、优化建议（按可行性 × 收益排序）

### 根因

IVF `materialize_candidates` 对 50 个候选行做随机 Parquet 读取：
- 每个随机读：打开文件 → 读取完整 Parquet page（~4MB）→ 解码 → 抽取目标行
- 50 × 4MB = **200MB 随机读 → 20s**（吞吐 ~10KB/s）
- FullScan **顺序读** 3.6GB → 5.6s（吞吐 ~650MB/s）

nprobe 1/4/16 耗时相同，确认瓶颈不在索引搜索而在 Parquet 回表。

### ~~P0: Row Group 文件内剪枝~~ ✅ 已完成 (2026-07-21)

**对任意 SELECT 有效**（包括 `SELECT *`）。50 个候选行来自 ≤20 个文件。用 `ParquetRecordBatchStreamBuilder::with_row_groups()` 跳过不含候选行的 row group，只解码 1-2 个目标 row group 而非全部 50 个。

**实测 IVF**：19.8s → **5.5s (-72.2%)**

改动：`iceberg-index/reader.rs` — 新增 `read_single_file_row_groups()` (~170 行)，调用点 fallback。分支 `feat/row-group-pruning`。

详见 [[批量回表_RowGroup剪枝_设计方案]]

### P1: FullScan 大页内存

FullScan 56% 在内核 I/O。2MB huge pages。
预估：5.6s → **~4.5s (-20%)**

### P2: 消 tokio

FullScan I/O 路径 tokio poll ~16%。与 SIFT 一致。
预估：5.6s → **~5.0s (-11%)**

### P3（远期）: 列裁剪

需要同时改 FDW（IVF 路径不投影 vec）和 bridge（透传 projected_columns），且 IVFFlat 才可行（避免 PQ 重排序需要 vec）。不在近期计划中。
