# Parquet 压缩策略对比分析报告 — 2026-07-21

**测试环境**: openEuler 24.03, 96核, 723GB, kernel 6.6.0-28
**数据集**: SIFT1M (128-dim), fixed(512), bucket(id, 16), IVFPQ nc=256

---

## 一、背景

`vector→fixed` 类型改造完成后，Parquet 嵌套解码（RLE+Rep/Def+ListArray）从 39% CPU 降为 0%。但 Zstd 解压（`ZSTD_decompressSequences`）随之跃升为 **第一大 CPU 热点（6-33% 占比）**。

本次测试对比三种 Parquet 压缩策略：
- **zstd**（当前默认）
- **lz4**（快速压缩）
- **uncompressed**（无压缩）

---

## 二、修改方式

仅修改 `setup_fixed.py` —— 在导入数据前向 Iceberg metadata JSON 注入 `write.parquet.compression-codec` 属性。pyiceberg 在写 Parquet 时读取该属性并传递给 PyArrow。

```python
# setup_fixed.py 新增参数
--compression {zstd,lz4,snappy,gzip,uncompressed}  # 默认 zstd
```

**Bridge / C++ / Rust 侧零改动**。Arrow Parquet reader 自动识别文件头中的压缩编码。

## 四、存储对比

| 压缩 | 大小 | vs Zstd |
|------|------|:--:|
| zstd | 147MB | 基准 |
| lz4 | 215MB | +46% |
| uncompressed | 500MB | +240% |

> SIFT `fixed(512)` 的 float 数据接近随机分布，压缩率有限。500MB = 1M 行 × 512B/行，基本等于原始数据大小。Zstd 仍能压缩 70%（147/500），但代价是高昂的解压 CPU。

## 五、延迟对比

### DOP=8（并行，生产场景）

```
  K       zstd       lz4      none    lz4提升  none提升
  ──────────────────────────────────────────────────────
  K=10     1176      1147      1052    -2.5%   -10.5%
  K=100    1408      1156      1296   -17.9%    -8.0%
  K=10000   1313      1131      1323   -13.9%    +0.8%
```

**结论**：
- **K=10**: 无压缩最快（读数据量小，I/O 不是瓶颈 → 省解压全收益）
- **K≥100**: LZ4 最优（读数据量增大 → 压缩率的 I/O 节省抵消解压开销）
- **LZ4 K=100 收益最大（-17.9%）**：K=100 时回表行数适中，解压开销占比最高

### DOP=1（串行）

```
  K       zstd       lz4      none
  ──────────────────────────────────
  K=10     4529      4920      3934
  K=100    6035      6552      5520
  K=10000   8417      6053      6243
```

串行下 LZ4 反而更慢（数据多读 46%，单线程 I/O 瓶颈）。这个场景少用——生产环境分区表通常开并行。

## 七、结论与建议

### 7.1 核心结论

| 问题 | 答案 |
|------|------|
| Zstd 解压开销能省多少？ | K=100 省 **17.9%**，火焰图确认 Zstd 热点完全消失 |
| LZ4 vs 无压缩选哪个？ | **LZ4**——大 K 场景更优，存储代价可接受（+46%） |
| 需要改 Rust/C++ 吗？ | **不需要**——仅改 Python 写 Parquet 时的压缩参数 |
| 存储代价多大？ | +46%（147→215MB），对 1M 级数据集可忽略 |

### 7.2 建议

1. **`setup_fixed.py` 默认压缩改为 `lz4`**：一句配置改动，14-18% 性能提升
2. **存量 zstd 表可逐步重导**：不影响查询正确性，按需迁移
3. **GIST 高维数据建议同测**：960 维时数据量 7.5×，I/O 影响更大，压缩 vs I/O 的 trade-off 可能不同
