## 三、优化详情

> 按实施时间顺序排列。后续新增优化追加到本节末尾。

### 3.1 vector→fixed 类型改造 ✅

**问题**: 原始 `vector(n)` 存储为 Iceberg `list<float>` → Parquet 嵌套类型。每行需处理 Repetition/Definition levels + RLE 编解码，Parquet 解码中嵌套开销占 ~39% CPU。

**方案**: 将存储类型改为 `fixed(n*4)` → Parquet `FIXED_LEN_BYTE_ARRAY` → Arrow `FixedSizeBinary`。消除嵌套，直接 memcpy。

**改动**: 涉及 3 个仓 — [iceberg_fdw](https://github.com/Doreami/iceberg_fdw/commits/feat/vector-fixed-type)（类型映射+物化）、[openGauss-Catalog](https://github.com/Doreami/openGauss-Catalog/commits/feat/vector-fixed-type)（fdw_util 支持 fixed[L] 语法）、[iceberg-index](https://github.com/Doreami/iceberg-index/commits/feat/vector-fixed-type)（IVF 插件新增 FixedBinary 变体）。

| 场景                 | list<float> | fixed    | 改善         |
| ------------------ |:-----------:|:--------:|:----------:|
| SIFT IVF K=10      | 1,044ms     | 606ms    | **-41.9%** |
| GIST IVF K=10      | 7,031ms     | 5,679ms  | -19.2%     |
| GIST FullScan K=10 | 21,143ms    | 15,428ms | -27.0%     |

> 注：此阶段使用 IVFFlat nc=1024 索引，非当前默认的 IVFPQ。

**收益分析**: 维度越高收益越小——GIST 960d 即使消除嵌套，vec 列 3840B 的解码仍是主要开销。SIFT 128d 的嵌套开销占比高，收益更明显。

**风险**: pyiceberg 不兼容 Iceberg v3 metadata（需 patch format-version 3→2）；StaticTable 只读，需改用 SqlCatalog + register_table；re-register 丢失 vector 类型。

**设计文档**: `fixed类型改造设计文档.md`

---

### 3.2 Parquet 压缩消除 ✅

**问题**: 默认 zstd 压缩消耗 CPU 解压。vector→fixed 后 `ZSTD_decompress` 成为火焰图 #1 热点（~33%）。GIST 高维随机向量压缩率极低（仅 14%），解压开销反而成主导。

**方案**: 所有新建表默认 Parquet 压缩改为 `uncompressed`。

**改动**: 导数据脚本默认参数从 zstd 改为 uncompressed。

| 场景                 | zstd     | uncompressed | 改善         |
| ------------------ | -------- | ------------ |:----------:|
| SIFT IVF K=10      | 1,176ms  | 1,052ms      | -10.5%     |
| GIST FullScan K=10 | 11,071ms | 5,585ms      | **-49.6%** |

**收益分析**: 低维数据压缩率高（SIFT 70%），解压开销小，收益有限。高维随机数据（GIST 960d）几乎不可压缩，解压开销反超收益。

**火焰图验证**: `ZSTD_decompress` 热点完全消失。

**风险**: SIFT 存储 147MB→500MB (+240%)，GIST 3.1GB→3.6GB (+16%)。本地磁盘可接受。

**设计文档**: `Parquet压缩策略对比分析_2026-07-21.md`

---

### 3.3 SipHash → FxHash ✅

**问题**: IVF `materialize_candidates()` 内部 HashMap join 使用标准库 SipHash（DoS 安全但慢），火焰图显示 `sip::Hasher::write` 占 4.06% CPU。

**方案**: 替换为 `FxHashMap`（rustc-hash crate），基于乘法+移位的高速哈希。内部 key 为 Iceberg 行地址，非外部输入，无 DoS 风险。

**改动**: bridge 内 4 处 `HashMap` 替换为 `FxHashMap`。分支 [`feat/siphash-to-fxhash`](https://github.com/Doreami/iceberg-index/commits/feat/siphash-to-fxhash)。

| K     | SipHash | FxHash  | 改善        |
| ----- | ------- | ------- |:---------:|
| 10    | 2,295ms | 2,255ms | -1.7%     |
| 100   | 3,404ms | 3,354ms | -1.5%     |
| 10000 | 4,028ms | 3,889ms | **-3.5%** |

**收益**: K=10 时 -1.7%，K=100 时 -1.5%，K=10000 时 -3.5%。收益随候选行数增加而提升——候选越多 HashMap join 开销越大，哈希替换的收益越明显。

> 火焰图热点（4.06%）不能直接推墙钟收益：CPU 采样反映的是 CPU 繁忙期间的占比，但 I/O 等待期间 CPU 空闲，4% 的热点被 I/O 占比稀释后墙钟改善不足 4%。详见踩坑记录 7.2。

**火焰图验证**: `sip::Hasher::write` 热点完全消失。

**风险**: FxHash 不防 HashDoS。bridge 内部 key 非外部输入，无此风险。

**设计文档**: `无压缩火焰图分析_后续优化路径_2026-07-21.md`

---

### 3.4 Row Group 文件内剪枝 ❌ 无效

**问题**: IVF 候选行分布在多个 Parquet 文件中，每个文件全量解码 vec 列。

**假设**: 用 Parquet row group 过滤跳过不含候选行的 row group，减少解码量。预估 GIST IVF -60~75%。

**方案**: bridge 内新增 row group 级别过滤方法，利用 Iceberg 已有的异步读取接口按 row group 粒度跳过无关数据。小文件（≤10K 行）跳过此路径避免 metadata 开销。

**改动**: 分支 [`feat/row-group-pruning`](https://github.com/Doreami/iceberg-index/commits/feat/row-group-pruning)。

**同环境对比**（同一次 stop→build→deploy→start 周期）:

|               | fxhash 基线 | row-group-pruning | 改善    |
| ------------- |:---------:|:-----------------:|:-----:|
| GIST IVF K=10 | 5,673ms   | 5,615ms           | -1.0% |
| SIFT IVF K=10 | 1,270ms   | 1,300ms           | +2.4% |

无差异，在噪声范围内。

**失败根因**：GIST 每个文件只有 **1 个 row group**（192MB/文件，50K 行）。实测 20 个文件共 25 个 row group，仅 5 个文件含 2 个 row group。单 row group 的文件无法做任何剪枝，优化从根上不成立。之前推测的 OS page cache、footer 开销、物化转换等均非主要原因。

**设计文档**: `批量回表_RowGroup剪枝_设计方案.md`

---

### 3.5 FDW 列裁剪 ❌ 不可行

**问题**: 理论上 `SELECT id` 可跳过 vec 列的 Parquet 解码，减少 I/O。

**分析**:

- gaussdb VectorSearch 节点需要 vec 列做精确 L2 重排序（PQ 码本返回近似距离，需用原始向量校准）
- FDW 设计文档明确索引路径 `projected_columns` = 整表全列，bridge 输出「全列 + `_distance`」
- bridge 侧 `scan_single_file` 写死读全列（注释原文："read the full row, back-to-table use case"）

**结论**: 三层设计封堵，且仅对 `SELECT id` 有效（正常 benchmark 为 `SELECT *`），不做。

---

### 3.6 Parquet 稀疏行读取（RowSelection）✅

**问题**: IVF 回表 `scan_single_file` 全文件解码后只取 2-3 行，99% 数据被丢弃。

**方案**: 利用 parquet-rs 底层 `RowSelection` 能力，把 IVF 索引返回的 `row_positions` → `FileScanTask.row_offsets` → pipeline 内转 `RowSelection` → parquet reader 只解码目标行。

**改动**: 涉及 2 个仓 — [iceberg-rust-datainfra](https://github.com/Doreami/iceberg-rust-datainfra/tree/feat/sparse-row-take)（`FileScanTask` + `build_row_selection_from_row_offsets` + pipeline 集成，+100 行）、[iceberg-index](https://github.com/Doreami/iceberg-index/tree/feat/sparse-row-take)（`scan_single_file` 传 `row_positions`，+9 行）。

| K     | fxhash 基线 | sparse-row-take | 改善         |
|:-----:|:---------:|:---------------:|:----------:|
| 1     | 19,056ms  | 19,019ms        | -0.2%      |
| 10    | 19,975ms  | 18,467ms        | -7.6%      |
| 100   | 20,086ms  | 18,929ms        | -5.8%      |
| 1000  | 21,350ms  | 18,699ms        | **-12.4%** |
| 10000 | 26,321ms  | 19,152ms        | **-27.2%** |

**收益**: 稀疏 take 让延迟与候选数量解耦——K=1~10000 全在 ~19s，fxhash 则随 K 线性增长。K=10000 时 -27%。火焰图证实 `materialize_projection_row`、`datumCopy`、`InitVector`、`AllocSetAlloc` 全部消失，应用层物化开销被 RowSelection 消除。RowSelection 天然覆盖 row group 跳过，row group 剪枝（3.4）独立实现不再需要。

**设计文档**: `2026-07-22-row-group-pruning/稀疏回表_设计方案.md` `稀疏回表_测试报告.md`

## 四、参考测试数据

> 以下为历史测试，不在当前优化路径上，供对比参考。

### 4.1 IVFFlat vs IVFPQ

优化过程中索引算法从 IVFFlat 切换到了 IVFPQ，两者取舍如下：

|           | IVFFlat       | IVFPQ                 |
| --------- |:-------------:|:---------------------:|
| 原理        | 原始向量聚类 + 精确距离 | PQ 压缩聚类 + 近似距离 + 精确重排 |
| SIFT 索引大小 | ~500 MB       | ~300 MB               |
| 精度        | 精确（无压缩损失）     | 有损（PQ 量化误差）           |
| 使用时期      | 7/15 ~ 7/18   | 7/20 起为默认             |

以下数据均来自 fixed 类型阶段（vector→fixed 已生效，zstd 压缩，SipHash，DOP=1）：

| 场景                     | IVFFlat nc=1024 | IVFPQ nc=256 |
| ---------------------- |:---------------:|:------------:|
| SIFT IVF K=10 (DOP=1)  | 606ms           | 4,225ms      |
| SIFT IVF K=100 (DOP=1) | —               | 5,445ms      |

> 均为 DOP=1。IVFFlat 的 606ms 来自无分区表，IVFPQ 的 4,225ms 来自 bucket(id,16) 分区表，分区开销包含在内。两者不可直接相减，仅说明 IVFFlat 在单分区场景下更快。后续所有优化和测试均基于 IVFPQ。

### 串行 vs 并行对照

以 SIFT IVF K=10 为例（当前串行基线 vs 并行测试，两列优化栈不同，不可直接相减）：

| 属性   | 串行（当前基线）                      | 并行 DOP=8（历史）             |
| ---- | ----------------------------- | ------------------------ |
| 延迟   | 1,270ms                       | 1,184ms                  |
| 优化栈  | fixed + uncompressed + FxHash | fixed + zstd + SipHash   |
| 分区   | 无分区                           | bucket(id,16)            |
| 加速来源 | —                             | 16 分区并行 + gaussdb 并行距离计算 |

> 并行（DOP=1→8 约 4-5×）与串行优化（压缩+FxHash）的收益可叠加。

### 关键发现

- IVF 并行扩展良好（DOP=1→8 约 4-5×），索引搜索和距离计算在 gaussdb 内可并行执行，数据读取锁短暂
- FullScan 几乎无扩展——推测原因为 bridge 全局锁 `BLOCK_ON_LOCK` 将所有文件读取序列化
- 饱和点 DOP=8~16，之后加速比趋近 1.0×
- 64 分区退化严重：DOP=64 时 SIFT 延迟反超 DOP=1（5,189ms vs 3,635ms），推测原因包括 gaussdb `UndoZoneLock` 竞争、bridge 全局锁、文件碎片化

sparse K=1、K=10、K=10000 火焰图形状几乎一致——应用层物化函数全部缺失，索引搜索 + Parquet 底层解码占主导。验证了"sparse 延迟不随 K 增长"的性能特征。

### 5.4 FullScan 热点

`ExecSort`（1M 行排序）主导，其次为 `iceberg_arrow_materialize_projection_row`、`datumCopy`、heap tuple 构建函数。FullScan 走顺序流式读取，优势在于 SDK reader 的流式 pipeline。

## 六、当前瓶颈分析

### IVF 路径

IVF 索引搜索不到 10ms，延迟主体在**回表取数据**。当前 GIST 共 20 个文件（每文件 ~180MB，1 row group），50 个候选行几乎命中全部文件。sparse-row-take 已消除应用层物化开销（`materialize_projection_row`/`datumCopy`），瓶颈转移为：

| 层级          | 开销  | 说明                                                                      |
| ----------- |:---:| ----------------------------------------------------------------------- |
| 串行读取        | 主导  | `scan_single_file` 每文件独立启动读会话，纯串行无并发。FullScan 的 SDK reader 一次传 20 文件并行读 |
| 单文件读会话开销    | 中   | 每次独立 open → footer → seek page，无法复用 OS read-ahead                       |
| Parquet 页读取 | 低   | RowSelection 精确选页，已大幅减少                                                 |
| 索引搜索        | 低   | IVFPQ 聚类遍历，<50ms                                                        |

**IVF 相比 FullScan 劣势**：

- **主因：并发缺失**。FullScan 的 SDK reader 内置多文件并发（`concurrency_limit_data_files`=CPU 核数），20 个文件并行读取。IVF 的 `scan_single_file` 是纯串行循环——每次只传 1 个文件，reader 有并发能力但无事可做。
- **次因：读取模式**。FullScan 统一 pipeline 能利用 OS read-ahead 批量预取；IVF 20 次独立读会话，每次重新"热身"，缺页效率只有 FullScan 的 1/3。

**perf stat 验证**（GIST K=10）：

| 指标                | IVF       | FullScan   | 说明                  |
| ----------------- |:---------:|:----------:| ------------------- |
| page-faults       | 1,219,875 | 1,062,461  | 缺页次数接近（1.15×）       |
| task-clock（CPU时间） | 20,232ms  | 6,345ms    | IVF CPU 时间 3.2×     |
| 缺页速率              | 60K/s     | **167K/s** | FullScan 2.8× 于 IVF |
| 墙钟                | 19.99s    | 5.46s      | 3.7×                |

缺页总数接近，但 FullScan 缺页速率 2.8× 于 IVF。主因是多文件并发让 CPU 时间被充分利用，次因是统一 pipeline 的 read-ahead 效率更高。IVF 串行读单文件时大量时间花在等待文件 open 和缺页处理上，CPU 闲置。

### FullScan 路径

FullScan 通过 SDK `to_arrow()` 顺序流式读取全部文件，瓶颈在 gaussdb 侧：

| 层级           | 开销  | 说明                          |
| ------------ |:---:| --------------------------- |
| 排序（ExecSort） | 主导  | 1M 行按距离排序                   |
| 距离计算         | 中   | 1M 次 L2 距离                  |
| Bridge I/O   | 低   | 3.6GB 顺序读取，OS read-ahead 优化 |

### 优化方向总结

| 瓶颈        | 已做                | 可做                          | 适用路径 |
| --------- | ----------------- | --------------------------- |:----:|
| 应用层物化     | ✅ sparse-row-take | —                           | IVF  |
| 文件级固定开销   | —                 | 回表管线统一（合并为单次 SDK reader 调用） | IVF  |
| 候选文件命中数   | —                 | 数据按向量聚类分区                   | IVF  |
| Bridge 调度 | —                 | 消除 tokio                    | 整体   |

## 八、踩坑记录

### 7.1 虚假基线

Row group 剪枝最初报告 GIST IVF 改善 72%（19.8s→5.5s），但后续同环境对比发现完全无差异。原因：19.8s 基线来自不同时期（同一服务器但负载、cache 冷热不同），与优化后的数据不可比。

**教训**: 任何性能对比必须在同一次 stop→build→deploy→start 周期内完成。不同时段的测量结果不能直接相减。

### 7.2 火焰图热点 ≠ 墙钟收益

SipHash 占 4.06% CPU 火焰图热点，但替换为 FxHash 后墙钟仅改善 1.5-3.5%。CPU 采样反映的是"CPU 时间占比"，但 I/O 等待期间 CPU 不消耗——4% 的 CPU 热点被 I/O 稀释后，墙钟收益远小于 4%。

**教训**: 火焰图热点是优化方向的线索，但不能直接用热点百分比预估墙钟收益。

### 7.3 高维数据压缩几乎无效

GIST 960d 随机向量 zstd 仅压缩 14%（3.6GB→3.1GB），但解压 CPU 开销让 FullScan 从 5.6s 飙升到 11.1s。默认压缩反而成负优化。

**教训**: 高维随机数据的压缩率极低，应默认关闭压缩。

### 7.4 GIST 索引构建残留

GIST 索引构建中断后 Puffin 文件不会自动清理，需手动删除残留。构建耗时与服务器负载相关（空闲时约 12 分钟，高负载时可达 60+ 分钟）。
