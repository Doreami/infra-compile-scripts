## 二、建表 & 建索引 SQL

### 建表

```sql
CREATE SERVER iceberg_catalog_server FOREIGN DATA WRAPPER iceberg_fdw;

CREATE FOREIGN TABLE sift_ns.sift1m (id bigint, vec vector(128))
SERVER iceberg_catalog_server OPTIONS (namespace 'sift_ns', table_name 'sift1m');

INSERT INTO iceberg_catalog.tables_internal(relid, namespace, table_name, table_uuid, metadata_location, ...)
VALUES ('sift_ns.sift1m'::regclass, 'sift_ns', 'sift1m', ...);
```

### Btree 索引

```sql
SELECT iceberg_catalog.create_index(
    'sift_ns', 'sift1m', 'idx_btree_id',
    '["id"]'::jsonb,
    'btree', 'btree',
    '{"key_column":"id"}'::jsonb
);
```

### IVF 向量索引

```sql
SELECT iceberg_catalog.create_index(
    'sift_ns', 'sift1m', 'idx_ivf_vec',
    '["vec"]'::jsonb,
    'ivf_flat', 'ivf',
    '{"num_clusters":1024, "sample_rate":100000}'::jsonb
);
```

索引文件: `indices/default/builtin.ivf_flat_v2_idx_ivf_vec_*.puffin` (502 MB)，构建耗时较长 (1M 向量 × 128 维 × 1024 聚类)

## 三、测试方法

- 耗时来源: `EXPLAIN (ANALYZE)` 的 `Total runtime`
- 每组测试跑 3 次取平均值，避免性能波动
- 查询向量: 取 id=1 的 128 维 float 向量常量（子查询会阻止索引匹配）
- 全扫参数: `enable_indexscan = off`, `enable_bitmapscan = off`
- IVF 参数: `enable_vectorsearch = on`, `try_vector_engine_strategy = force`

---

### 测试项 1: Btree 点查

**说明**: 先删索引测全扫，再建索引测索引扫，对比性能。

**SQL**:

```sql
SELECT * FROM sift_ns.sift1m WHERE id = 500000;
```

|          | Run1 | Run2 | Run3 | 平均         |
| -------- | ---- | ---- | ---- | ---------- |
| 无索引 (全扫) | 96   | 67   | 66   | **76 ms**  |
| btree 索引 | 178  | 176  | 170  | **175 ms** |

> 全扫反而更快，但两者都在 200ms 以内：Iceberg 文件级 min/max 裁剪使单值查仅命中 1 个文件，btree 索引查找 + 回表反而增加开销。点查场景整体耗时极低，索引优势不显著。

---

### 测试项 2: 全表扫描 (Baseline, 4 组 Top-K)

**说明**: 关闭所有索引，每次遍历 100 万行计算 L2 距离并排序。

```sql
SET enable_indexscan = off; SET enable_bitmapscan = off;
SELECT id FROM sift_ns.sift1m
ORDER BY vec <-> '[...]'::vector LIMIT <K>;
```

| K   | Run1  | Run2  | Run3  | 平均           |
| --- | ----- | ----- | ----- | ------------ |
| 10  | 2,420 | 2,454 | 2,435 | **2,436 ms** |
| 50  | 2,424 | 2,440 | 2,437 | **2,434 ms** |
| 100 | 2,433 | 2,436 | 2,439 | **2,436 ms** |
| 500 | 2,422 | 2,448 | 2,434 | **2,435 ms** |

> 全扫耗时与 K 无关（均需遍历全部 100 万行），稳定在 ~2,435 ms。

## 五、总结

1. **Btree 点查**: 全扫 76ms vs 索引 175ms，均在 200ms 以内。Iceberg 文件级 min/max 裁剪使单值查仅命中 1 个文件，btree 索引查找 + 回表反而更慢。点查场景整体极快，走不走索引差异不大。
2. **IVF 向量索引正常**: Top-10 加速 2.9×（839ms vs 2,436ms），K=1M 时加速回升至 1.82×（1,727ms vs 3,135ms）。向量常量必须直接写在 SQL 中，子查询阻止索引匹配。
3. **IVF 耗时封顶 ~1,700ms**: K=10 到 K=1M，IVF 始终在 ~1,700ms；全扫随 K 增长（排序开销），从 2,436ms → 3,135ms。K 越大 IVF 优势越明显。
4. **冷启动 & 构建成本**: 首次 IVF 搜索有索引加载开销（~3,118ms），预热后稳定。IVF 构建耗时长（1M 向量 × 128 维 × 1024 聚类，产出 502MB），btree 构建秒级完成。
