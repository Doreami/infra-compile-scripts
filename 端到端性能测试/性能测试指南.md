### 2.4 火焰图采集

```bash
cd ~/infra-compile-scripts/端到端性能测试/

# SIFT1M
# 默认场景覆盖
python3 run_flamegraph.py --serial --dataset sift --namespace sift_ns --table sift1m

# GIST1M
python3 run_flamegraph.py --serial --dataset gist --namespace gist_ns --table gist1m_none --scenarios ivf_k10
```

通用脚本 `run_flamegraph.py`，默认场景覆盖 FullScan + IVF 多 K 值。`--serial` 跳过并行 DOP 场景。

> **已知问题**：`run_flamegraph.py` 使用 `pgrep -f "gaussdb.*37000"` 获取 PID，会匹配 bash wrapper 而非 gaussdb 主进程，导致 perf 采集 0 样本。手动采集时用 `pgrep -x gaussdb` 替代。手动方法见第八节。

**前置条件 — 编译时保留帧指针**：

火焰图依赖 `perf record -g` 做调用栈回溯。Release 编译默认会省略帧指针（`-fomit-frame-pointer`），导致调用栈错乱。需要：

```bash
# bridge (Rust)
RUSTFLAGS="-C force-frame-pointers=yes" cargo build --release

# gaussdb (C/C++)
./configure CFLAGS="-fno-omit-frame-pointer" CXXFLAGS="-fno-omit-frame-pointer"
```

性能影响约 0-2%，可忽略。如果不加帧指针，`-g` 回溯的火焰图会出现函数顺序错位（如 `GaussDbThreadMain` 骑在 `libc.so` 上面）。不想改编译就只能用 `--call-graph dwarf`，但采集慢 6 倍。

- 如果版本一致则标注"服务器代码与本地代码一致"

### 2.8 性能优化分析的时机

性能优化分析是消耗较大的工作（需通读代码、追踪调用链、设计修改方案），**不需要每次测试都做**，且应**增量进行**而非从零开始。

| 情况                       | 是否分析 | 方式                        |
| ------------------------ |:----:| ------------------------- |
| 代码有 commit 变更            | ✅    | **增量分析**：只分析变更部分，其余引用上次报告 |
| 首次测试新数据集，验证优化方向          | ✅    | 引用上次分析框架，补充新数据验证          |
| 仅重复测试，代码无变更              | ❌    | 跳过                        |
| 仅调参（nprobe、num_clusters） | ❌    | 跳过                        |

**增量分析流程**：

1. 对比当前 commit 与上次分析时的 commit，找到变更的组件
2. 只重新分析变更组件涉及的代码路径
3. 未变更部分直接引用上次报告的结论（标注 "同 YYYY-MM-DD 报告第 X 节"）
4. 如果有新发现（如 GIST 验证了内核占主导），追加章节
5. 更新版本信息表，增加"前次分析"一行

> 如跳过优化分析，`YYYY-MM-DD/` 目录只放性能测试报告 + 火焰图分析报告即可。

## 三、注意事项（踩坑记录）

### 3.1 查询向量必须用字面量

```sql
-- ❌ 子查询 → 不走索引（当前功能现状）
SELECT ... ORDER BY vec <-> (SELECT vec FROM t WHERE id=1)::vector LIMIT 10;

-- ✅ 字面量 → 走索引
SELECT ... ORDER BY vec <-> '[...]'::vector LIMIT 10;
```

### 3.2 create_index 参数

| 索引     | type 参数  | impl 参数 | properties                                                        |
| ------ | -------- | ------- | ----------------------------------------------------------------- |
| ivf_pq | `ivf_pq` | `ivf`   | `{"vector_column":"vec","num_clusters":256,"sample_rate":100000}` |

- `type` 和 `impl` 写成一样会报错
- `num_clusters` 不是 `nlist`，`sample_rate` 是整数行数不是比例

### 3.3 控制参数

| 参数                                   | 作用                             |
| ------------------------------------ | ------------------------------ |
| `enable_vectorsearch = on/off`       | 是否启用向量索引                       |
| `try_vector_engine_strategy = force` | 强制走向量引擎                        |
| `enable_indexscan = off`             | 关闭索引扫描（强制全扫）                   |
| `enable_bitmapscan = off`            | 关闭位图扫描                         |
| `query_dop`                          | **并行度**。`>1` 且表有分区元数据时触发分区并行扫描 |

### 3.4 冷启动

- 首次 IVF 搜索有 ~3s 的索引加载开销
- 用第一轮做预热，正式数据取后续轮次

### 3.5 火焰图采集要点

- **长查询（>1s）**: 1 轮即可，99Hz × 2.4s ≈ 240 samples
- **短查询（<1s）**: 循环重复，保证 >200 samples（如 btree 50 轮）
- `sleep 1.5` 等 perf 初始化，太短会导致空数据
- 每轮前先预热，避免冷启动混入

### 3.6 磁盘清理

多次 `drop_index + create_index` 会残留 puffin 文件（每次 ~500MB）。

```sql
-- 删孤儿文件
SELECT iceberg_catalog.remove_orphan_files('sift_ns', 'sift1m',
  older_than := '0 seconds'::interval, dry_run := false);
-- 清理过期快照 + 索引
SELECT iceberg_catalog.expire_snapshots('sift_ns', 'sift1m',
  older_than := '0 seconds'::interval, retain_last := 1,
  delete_files := true, include_index := true);
-- 清理旧 metadata
SELECT iceberg_catalog.cleanup_old_metadata('sift_ns', 'sift1m',
  older_than := '0 seconds'::interval, retain_last := 2, dry_run := false);
```

### 3.7 查看 perf 原始数据

火焰图 SVG 是可视化结果，`perf report` 是精确的数值来源。采集完成后可直接在服务器上分析。

**文件位置**：

```
端到端性能测试/YYYY-MM-DD/flamegraphs/perf_data/perf_<场景>_YYYY-MM-DD.data
```

**命令行模式**（输出文本报告）：

```bash
cd ~/infra-compile-scripts/端到端性能测试/2026-07-16/flamegraphs/perf_data

# 看 IVF K=10 的 Top-10 热点
perf report -i perf_ivf_k10_2026-07-16.data --stdio --percent-limit 0.5 --no-children

# 看全扫 K=10 对比
perf report -i perf_fullscan_k10_2026-07-16.data --stdio --percent-limit 0.5 --no-children

# 只看某个模块的函数
perf report -i perf_ivf_k10_2026-07-16.data --stdio | grep "libiceberg_rust_bridge"
```

**交互式 TUI 模式**（推荐，可以展开调用栈）：

```bash
perf report -i perf_ivf_k10_2026-07-16.data
```

| 按键      | 作用                 |
| ------- | ------------------ |
| `↑` `↓` | 上下移动               |
| `Enter` | 展开/折叠调用栈，可逐层下钻到源码级 |
| `+`     | 展开当前函数的调用者（Caller） |
| `/`     | 搜索函数名              |
| `q`     | 退出                 |

**输出列说明**：

```
Overhead  Command   Shared Object               Symbol
16.35%   worker    [unknown]                   [k] 0xffffffff9a201174
11.77%   worker    libiceberg_rust_bridge.so   [.] parquet::encodings::rle::RleDecoder::get_batch_with_dict
 2.40%   worker    gaussdb                     [.] LWLockRelease(LWLock*)
```

| 列               | 含义                                                         |
| --------------- | ---------------------------------------------------------- |
| `Overhead`      | 该函数独占的 CPU 采样占比                                            |
| `Command`       | 进程/线程名（worker = gaussdb 工作线程, tokio-rt-worker = Rust 异步线程） |
| `Shared Object` | 函数所属的 `.so` 或可执行文件 — **用来判断函数来自哪个模块**                      |
| `Symbol`        | 函数名。`[k]` = 内核态，`[.]` = 用户态                                |

**Shared Object 对照表**：

| Shared Object               | 对应模块                          |
| --------------------------- | ----------------------------- |
| `libiceberg_rust_bridge.so` | Rust 桥接层（Parquet 解码、索引引擎、压缩）  |
| `gaussdb`                   | openGauss 主程序（锁、缓存、undo、内存管理） |
| `libc.so.6`                 | C 标准库                         |
| `[unknown]`                 | 内核态或缺少符号                      |

## 四、怎么看结果

### 4.1 耗时对比（EXPLAIN ANALYZE）

```
全扫 K=10:  2,436ms  │  ████████████████████████
IVF  K=10:    839ms  │  ████████           (2.9×)
```

关注：

- **加速比** = 全扫耗时 / 索引耗时（越大越好）
- **K 值变化**：K 越大全扫排序开销越大，IVF 有封顶效应

### 4.2 火焰图读法

```
┌──────────────────────────────────────────────┐
│  func_a()  │  func_b()  │ func_c() │ func_d()│  ← 上层调用者
├──────────────────────────────────────────────┤
│        func_x()        │    func_y()          │  ← 中层
├──────────────────────────────────────────────┤
│              func_kernel()                    │  ← 底层/内核
└──────────────────────────────────────────────┘
```

- **X 轴宽度** = CPU 时间占比（越宽越热）
- **Y 轴高度** = 调用栈深度（上层调用下层）
- **颜色**: 暖色 = 用户态代码，冷色 = 内核态
- **点击** 可聚焦放大，**搜索** 可定位函数

### 4.3 读 perf report

```
Samples: 410  of event 'cycles:Pu'
# Overhead  Shared Object              Symbol
  18.57%    libiceberg_rust_bridge.so  RleDecoder::get_batch_with_dict
```

- `Overhead` = 该函数独占的 CPU 采样占比
- `Shared Object` = 所属 .so / 可执行文件
- `[unknown]` = 缺少调试符号（常见于内核或 stripped 的 lib）

## 五、怎么进行分析

### 5.1 识别最大热点

在 `perf report --stdio | head -20` 中看 Top-5：

- 如果 **Parquet 解码函数（RLE/Rep/Def Level/ListArray）** 占 >30% → 瓶颈在数据读取
- 如果 **向量距离计算** 占 >10% → 瓶颈在数学运算
- 如果 **内核开销** 占 >15% → 瓶颈在 I/O 或内存

### 5.2 全扫 vs 索引扫对比

| 对比维度      | 方法                      |
| --------- | ----------------------- |
| 热点函数是否相同  | 看两份 perf report 的 Top-5 |
| 索引新增了什么开销 | 看 IVF 火焰图多了哪些函数         |
| 索引省掉了什么开销 | 看全扫火焰图有哪些函数在 IVF 中缩小/消失 |

### 5.3 实战案例：SIFT1M 分析

> 以下基于 2026-07-15 测试（IVFFlat + `list<float>` 类型），当时尚未做 fixed 类型改造和 sparse-row-take。当前架构下结论已不同，保留作为分析方法参考。

| 关键发现                         | 数据依据                                 |
| ---------------------------- | ------------------------------------ |
| **Parquet 解码是最大瓶颈** (35-40%) | RLE+ListArray+Rep/Def Level 占据 Top-5 |
| **向量索引搜索开销可忽略** (<3%)        | IVF 火焰图中索引查找函数未进入 Top-5              |
| **IVF 加速靠减少行数**              | 单行处理成本不变，扫描量从 100 万降到聚类子集            |

```bash

  $gsql -d postgres -p 37000 -f /tmp/q.sql > /dev/null 2>&1
done

# 杀 perf 并生成火焰图
```

### 8.7 关键注意事项

| 事项                         | 说明                                                                                                               |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **验证 .so 身份**              | 每次切分支后 `md5sum` 确认两个 .so 不同，曾出现 .so.sparse 被误复制为 fxhash 副本导致半天 A/B 测试白做                                          |
| **pgrep 精确匹配**             | 用 `pgrep -x gaussdb` 而非 `pgrep -f gaussdb`，否则匹配到 bash wrapper 导致 perf 0 样本                                       |
| **同会话测试**                  | A/B 对比必须在同一次 gaussdb 启停周期内完成                                                                                     |
| **SQL 用 -f**               | 向量字面量 `[0.0459,...]` 用 `-c` 传参不完整，必须 `-f` 传文件                                                                    |
| **先预热再采火焰图**               | 数据进 cache 后火焰图才看到真实热点，否则全是 `vma_alloc_folio` 等缺页处理                                                               |
| **EXPLAIN ANALYZE Timing** | `EXPLAIN ANALYZE` 的 `actual time` 只看 gaussdb executor 时间，不含 bridge I/O。对比 IVF 和 FullScan 要用墙钟或 `Total runtime` 行 |
| **火焰图 function 消失**        | `[unknown]` 来自内核模块，装 `kernel-debuginfo-$(uname -r)` 可减少                                                          |
