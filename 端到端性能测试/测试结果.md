## 已知问题

### #1 IVF 索引扫描返回 0 行（planner 正确，引擎返回空）

同上方查询 SQL，仅 `enable_vectorsearch` 设置不同：全扫返回 10 行，索引返回 0 行（详见上方查询结果对比表）。

> 默认 `ivfflat_probes = 1`，调到 32 同样返回 0 行。删掉索引后全扫正确返回，确认为 IVF 索引扫描路径 bug。

EXPLAIN 计划显示 planner 已正确选择 `Vector Search → bridge vector index scan`（见上方），但 Rust 引擎层 IVF search 未返回数据。**无法测 Recall，索引性能潜力明确（54x 加速）。**

### #2 btree 索引扫描返回 0 行

```sql
-- 无 WHERE（正常）
SELECT id FROM sift_ns.sift1m LIMIT 3;
-- 返回: 800001, 800002, 800003

-- 点查返回空
SELECT id FROM sift_ns.sift1m WHERE id = 800001;
-- 返回: (0 rows)
```

```
EXPLAIN: Foreign Scan → bridge scalar index scan (Index Name: idx_btree_id) → Filter Mode: recheck
```

btree 索引已 active，planner 正确选择 `bridge scalar index scan`，但执行返回空。删掉索引后全扫 + SDK Filter 正确返回，确认为 btree 索引扫描路径 bug。

### #3 子查询不走索引

```sql
-- 走全扫
SELECT id FROM sift_ns.sift1m ORDER BY vec <-> (SELECT vec FROM sift_ns.sift1m WHERE id=1) LIMIT 10;
-- EXPLAIN: bridge full scan（无 Vector Search 节点）

-- 走索引（必须用字面量）
```

## 结论

- **数据导入链路完整**：fvecs → Parquet → Iceberg → openGauss 全通，全扫路径已验证正确
- **索引 PLANNER 正确**：EXPLAIN 显示 Vector Search / Scalar Index Scan，正确选择索引
- **索引扫描路径有 bug**：#1 IVF 和 #2 btree 索引均返回 0 行，全扫同查询正常，定位为 iceberg-index 层问题
- **性能潜力明确**：索引扫描 0.047s vs 全扫 2.54s，快 **54 倍**（修复后预期）
