# 向量标量混合查询加速 · 现状流程内物化路径优化 详细设计

> 最后更新: 2026-08-25
> 状态: 新增（调研结论已按代码逐层核实；经评审修订：向量列必读约束（内核精确重排）、收益模型重算、fetch_k 公式、删除文件边界）
> 相关调研: 《设计文档/hybrid-index-research-report.md》
> 前置依赖: 向量 IVFPQ 索引、混合任务组数据面（现状向量索引配置 `vector_raw_rows_recheck`）、内核 VectorSearch 精确重排
> 定位: 现状流程内独立优化——**不新增标量索引、不改变候选集生成（fetch_k 召回上限不变）**，只降低现状混合查询的物化开销。

---

## 1. 概述

### 1.1 目标

为现状「向量检索 + 标量过滤」混合查询（现状 post-filter 流程）降低**物化开销**：

```sql
SELECT id FROM tab
WHERE category = 'electronics'
ORDER BY vec <-> '<query_vector>'::vector
LIMIT 10;
```

现状流程是「向量索引搜索 → fetch_k 候选行 → **全表列物化** → 内核精确重排 → 标量 recheck → 输出」。本方案把物化阶段改为**两阶段**：

```
fetch_k 候选行 → ① 只读标量列 → ② 谓词过滤出存活行 → ③ 仅存活行读输出列与向量列 → 输出
```

目标：**物化读量从「fetch_k × 全表宽度」降为「fetch_k × 标量列宽度 + 存活行 × (输出列 + 向量列 − 标量列)宽度」**，同时结果语义与现状完全一致（不改变 fetch_k 召回、不改变距离来源、不改变排序）。

### 1.2 非目标

- **不新增标量索引**（BTree）——候选集仍由向量检索的 fetch_k 决定。
- **不改变候选集生成 / 召回**——fetch_k 上限不变，高选择率下「存活行 < K」属现状语义，本方案不解决（候选集改进属索引级候选集预过滤，不在本文范围）。
- **不做索引级候选集预过滤 / 精确档**——本方案只优化现状路径的物化，不引入计数/枚举/路由。
- **不改距离来源**——内核从向量列精确重算距离的机制（现状）保持不变，向量列因此**必须保留在物化读集**（§1.3 核实要点②）。
- 不触碰向量排序（无相似度）、跨列 OR、NOT 等查询形态。

### 1.3 现状基线（物化路径，代码逐层核实）

| 环节 | 现状事实 |
|---|---|
| 候选生成 | 向量索引搜索返回 ≤ fetch_k 候选行（行地址 + 索引分）；**fetch_k = max(topK, clamp(topK×5, 50, 10000))** |
| 距离来源 | 索引码只用于**候选选择**（决定 fetch_k 收哪些行）；**最终距离在内核侧从物化行的向量列精确重算**，索引的 `_distance` 被桥接剥除、不使用 |
| 物化 | 按候选行号回表读 Parquet——**读全表 schema 的所有列**（含 960 维向量列），输出按 FDW 投影列裁剪 |
| 标量过滤 | 过滤列必然在输出投影内（本地 recheck 需要）；**谓词只在 FDW/执行器侧**，引擎的索引扫描请求不含标量谓词 |
| recheck | 执行器对物化行求值原谓词（最后防线），引擎不参与 |
| 列子集读 | 引擎其他读取路径已按列名列表选列（列级投影），**能力已具备，仅物化路径未用** |

> **核实要点**（与代码对齐，作为设计依据）：
> ① 物化读列取自「全表当前 schema 的全部列名」而非输出投影；② **向量列必读**——混合查询的计划中，ForeignScan 输出含排序键距离表达式（`vec <-> q`），执行器在其上对物化出的向量列求值得到精确距离，VectorSearch 节点读取该距离列做全局 top-K；索引的 `_distance` 被剥除不用。因此收窄读列**必须保留向量列**。实测 EXPLAIN 佐证：`SELECT c_integer ... ORDER BY c_vector <-> ... LIMIT 3`（向量列不在 SELECT 输出）的 ForeignScan 投影列为 `c_integer,c_vector`——向量列因排序键表达式被拉进读取投影；③ 索引扫描请求的投影列来自 FDW 输出投影（含标量过滤列与向量列）；④ 快速读取路径要求列集与全表一致，列数不匹配时自动退回通用读取路径（通用路径支持列级投影）；⑤ 引擎的索引扫描请求结构里向量与标量查询二选一，无标量过滤字段。
>
> **全列读的成因**：全列读是**索引物化路径独有**的——原生数据面（全扫/兜底）读取本就按输出投影列裁剪，仅索引回表物化复用了「按行号全行读」的通用原语、未做投影感知。FDW 不消费全部列，只按输出投影列接收；但**向量列是输出投影的成员**（排序键表达式引用它），并非无关列。索引扫描数据面的输出契约文档描述为「全表列 + _distance」，收窄输出时该契约需同步演进（§5.3）。唯一会额外消费物化结果里向量列的能力是内核精确重排，它**始终启用**——向量列始终须保留在读集。

实测基线（同环境 A/B 参考，`ORDER BY vec <-> q LIMIT K`，DOP=1）：

| 数据集 | 纯 IVF K=10 | 全扫 K=10 | 官方召回@10 |
|---|---|---|---|
| SIFT | 212ms | 2358ms | 90.6% |
| GIST | 1467ms | 18883ms | 78.4% |

物化是现状混合查询的最大耗时环节。

## 2. 问题分析：物化的浪费

现状物化有**两重**浪费：

### 2.1 浪费一：无关列全量物化（读列远超输出所需）

候选行按**全表 schema** 读取——输出只需 `[id, category]` 与向量列（供内核重排），实际却读入全部列。**向量列不是浪费**（内核重排需要，§1.3），浪费的是**无关非向量列**。这一重浪费与过滤率无关，但收益有限（取决于表里无关列的宽度与数量）。

### 2.2 浪费二：被标量过滤掉的行也全宽物化（含 960 维向量列）

fetch_k 候选行中不满足标量条件的行，其**全部列**（含 960 维向量列）都已被读入并解码，最终被 recheck 丢弃。候选内过滤率越高，浪费越大。**这是物化开销的主要来源**——向量列占表宽绝大部分，而它只为存活行（进内核重排的行）所需。

### 2.3 收益模型

```
现状物化读量  = fetch_k × 全表宽度（含 960 维向量列与全部无关列）
层级1 读量    = fetch_k × (输出列 ∪ 向量列) 宽度        ← 停读无关非向量列
层级2 读量    = fetch_k × 标量列 + 存活行 × (输出列 ∪ 向量列 − 标量列) 宽度
```

两层收益（**收益公式假设阶段 2 不重读标量列**——实现须共享存活行集合并携带阶段 1 列值；若阶段 2 对存活行重读完整投影会多读 `存活行 × 标量列宽度`，属退化形态）：

- **层级 1 收益（有限，与过滤率无关）**：停读**无关非向量列**。向量列必读（内核重排），不能省。收益取决于表里无关列的总宽度。
- **层级 2 收益（主价值，∝ 候选内过滤率）**：**被过滤行不读任何列，包括 960 维向量列**。向量列只对存活行读——这是本方案最大的收益来源：向量列占表宽绝大部分，而它只需为进内核重排的存活行而读。候选内过滤率 80% 时，向量列读量降至 20%。

> **推测（需实测，§7 测试条件）**：物化为现状混合查询最大耗时（基线实测），读量压缩比例可近似映射为物化耗时下降。层级 2 收益随候选内过滤率上升；向量列占表宽比例越高、过滤率越高，收益越大。具体数字以同环境 A/B 为准。

## 3. 总体方案：两阶段物化（标量先行 · 列读版）

### 3.1 两个递进层级（可独立落地）

| 层级 | 内容 | 谓词进引擎 | 收益 |
|---|---|---|---|
| **层级 1：投影感知物化** | 物化读列从「全表列」收窄到「输出列 ∪ 向量列」 | 否 | 停读无关非向量列（有限） |
| **层级 2：标量先行** | 标量谓词进引擎：先读标量列过滤，存活行再读输出列与向量列 | 是 | **被过滤行不读任何列（含向量列）**——主价值 |

**两个层级共享同一项底层能力——列子集读（投影感知物化）**，但**不是先后依赖关系**：层级 2 的两阶段本身就是列子集读（阶段 1 读标量列、阶段 2 读输出列∪向量列），**直接覆盖层级 1 的功能，不依赖层级 1 先落地**。层级 1 是同一能力的较浅应用，其独立价值有二：① 谓词不可下推（或暂未接入谓词）的查询上仍停读无关列；② 作为「先引入列子集读能力、无谓词形态低风险验证」的分步第一步（§6 Phase 1）。层级 2 需要把谓词传入引擎（§3.3），编排两阶段读。

> **为何层级 1 不能停读向量列**：混合查询的 ForeignScan 输出含排序键距离表达式 `vec <-> q`（§1.3 核实要点②），内核 VectorSearch 需要该距离列做全局 top-K。距离值由执行器对物化出的向量列求值得出，故向量列对**每个**候选行都必须物化。停读向量列需改变距离来源（改用索引近似分），改变召回语义，属本方案非目标。

### 3.2 执行时序（层级 2 全景）

```
向量索引搜索（现状，不变）        → fetch_k 候选行（行地址 + 索引分，仅用于候选选择）
                                      │
阶段 1：只读标量列（窄投影读）       → 对全部候选行读标量过滤列（如 category）
                                      │
谓词过滤（引擎内求值）              → 存活行（保持候选序；过滤精确，见 §5）
                                      │
阶段 2：存活行读输出列与向量列       → 非标量列的输出列（如 id）+ 向量列（供内核重排）
                                      │
组装配对                            → 存活行 [输出列, 向量列]（无 _distance）
                                      │
内核 VectorSearch（现状，不变）      → 执行器对向量列求值距离 → 全局 top-K
                                      │
FDW 本地 recheck + 物化（现状，不变）→ LIMIT K
```

- 阶段 1 读量为 `fetch_k × 标量列宽度`；阶段 2 读量为 `存活行 × (输出列 ∪ 向量列 − 标量列)宽度`。
- **向量列只对存活行读**：内核只见到存活行（引擎已过滤），被过滤行不进入内核、不需要向量列。这是层级 2 收益的核心。
- **标量列不重读**：阶段 1 已读的标量列值对存活行**直接沿用**（过滤后即保留存活行该列值），阶段 2 只读输出列中**非标量列**的部分与向量列，两阶段按存活行候选序拼接成输出行。实现须由两阶段共享存活行集合并携带阶段 1 列值；若实现为「阶段 2 对存活行独立重读完整投影」，会重复读标量列（多读 `存活行 × 标量列宽度`，通常很小但属退化形态），应避免。
- 存活行输出顺序 = 内核精确重排后的距离序（引擎阶段 1/2 的拼接序只影响输入顺序，不影响最终 top-K）。
- **落点说明（为什么在引擎侧）**：现状数据面是「单次扫描 → 返回物化行流」，无「先读标量列、再按存活行补读其余列」的往返接口，候选行地址也不越过接口边界；FDW 侧无法做两阶段。因此两阶段物化编排在引擎侧完成，FDW 只负责把谓词传下去并保留 recheck。

### 3.3 谓词进入引擎的方式

**现状**：向量索引配置只含向量查询（索引名、查询向量、距离度量、sql_k、fetch_k、检索参数）。标量谓词存在于两处——FDW 计划期的本地谓词，以及扫描过滤配置（仅用于文件级裁剪与兜底扫描），**索引扫描阶段完全不知道标量谓词**。

**方案**：在向量索引配置中增加可选 `scalar_filter`（标量过滤表达式），复用标量索引配置的表达式 JSON 格式（列 / 算子 / 值数组）。FDW 把可下推的本地谓词序列化进该字段；引擎对解码出的标量列值直接求值。

- 缺省无 `scalar_filter` = 现状纯向量检索（向后兼容）。
- 不依赖任何标量索引——这是「列读 + 求值」过滤，不是索引过滤。
- 只序列化**简单可下推谓词**（等值/范围 =、<、<=、>、>=；IN 属格式支持但 FDW 暂不翻译，§5.2/§7.2）；其余留在本地 recheck（§5.2）。

> **功能性与现状能力（代码已核实）**：标量表达式 JSON 格式（field_id / op / value）与结构（`ScalarExpression`、`ScalarOperator` 全算子、`ScalarValue` 全类型带全序）已存在——标量索引配置（`scalar_rows_recheck`）已用同一格式，FDW 把谓词序列化为表达式 JSON 的能力已具备。引擎对**解码列值求值**的原语已存在（现状实现覆盖 Int64 的 Eq/Lt/Le/Gt/Ge/In），按列名取 batch 列的模式已有（标量全扫路径）。**落地缺口**：把求值器泛化到全部值类型（Utf8 / Float64 / Bool）并输出**布尔掩码**（对齐候选行号）、支持**多表达式 AND** 组合——属引擎侧实现工作量，非设计风险。

### 3.4 列子集读

- 复用现有按列名列表选列的能力（引擎其他读取路径已用，§1.3），物化读原语加**列投影参数**。
- 窄读走通用读取路径；快速路径（整文件全列读取加速）在列数不匹配时自动退回通用路径（现状已具备该回退，§1.3 核实要点④）。
- **读集约束**：任意阶段的读集都必须**包含向量列**（内核重排需要，见 §1.3 核实要点②）；阶段 2 的读集 = 输出列 ∪ 向量列 − 标量列。
- 候选行按文件分组读取；阶段 1 / 阶段 2 各自独立窄读，结果按候选序重排拼接。

## 4. 数据流与请求结构

### 4.1 混合检索配置扩展

```
混合检索配置
├─ 向量侧（必填，沿用现状）
│   ├─ 向量索引名 / 查询向量 / 距离度量 / sql_k / fetch_k / 检索参数
└─ 标量过滤（可选，新增）
    └─ scalar_filter: [{column, op, value}, ...]（AND 组合；复用标量索引表达式 JSON 格式）
```

### 4.2 各层改动

| 层 | 改动 |
|---|---|
| **FDW** | 规划期把可下推本地谓词序列化为 `scalar_filter` 进向量索引配置；EXPLAIN 标注「物化优化：标量先行」及命中/回退 |
| **桥接** | 解析 `scalar_filter` 并透传进索引扫描请求 |
| **引擎/索引** | 编排两阶段物化（阶段 1 窄读标量列 → 求值过滤 → 阶段 2 窄读输出列 ∪ 向量列）；读原语加列投影参数 |
| **执行器** | 不变——本地 recheck 保留；内核 VectorSearch 精确重排机制不变（向量列仍在读集） |

## 5. 正确性与边界

### 5.1 正确性保证

| 层 | 机制 | 保证 |
|---|---|---|
| 引擎过滤 | 对解码列值精确求值 | 返回行必满足下推谓词（无假阳性）；**绝不为子集过滤**（谓词翻译精确或超集，§5.2） |
| 本地 recheck | FDW 保留完整原谓词 | 最终语义正确性最后防线（下推以外的谓词、翻译不精确的兜底） |
| 距离/排序 | 内核 VectorSearch 从向量列精确重算 + 全局 top-K（现状机制不变） | 排序正确（向量列始终在存活行的读集内） |
| 召回 | fetch_k 不变 | 与现状一致（本方案不改候选集） |

### 5.2 谓词翻译约束

- **可下推**：等值、范围（=、<、<=、>、>=），AND 组合。IN 属表达式格式支持（引擎求值器已实现 `ScalarOperator::In`），但 **FDW 当前不翻译 ScalarArrayOpExpr**，故实测不下推（§7.2 注）——作为后续增强。
- **不可下推**：其余形态（含空值语义复杂的、非列等式的）→ **不进行级过滤**，回退现状（物化仍按层级 1 收窄，语义不变）。
- **约束**：翻译必须保证「引擎过滤结果 ⊇ 真匹配」（精确或超集）。等值/范围在解码列值上求值即精确；若某算子翻译为超集（保守），由 recheck 修剪，结果仍正确。**禁止**翻译为子集（会丢真匹配）。
- **空值语义**：下推时须与执行器语义一致（如空值判断 / 三值逻辑），不一致的算子不下推。

### 5.3 边界与回退

| 场景 | 行为 |
|---|---|
| 候选内过滤率低（近 0%） | 层级 2 收益小，但层级 1「停读无关非向量列」仍在 |
| 无标量谓词 | 纯向量查询，走层级 1（物化只读输出列 ∪ 向量列），语义不变 |
| 存活行 < K | 现状语义（fetch_k 不变），不改变 |
| 输出列 == 标量列（`SELECT category ...`） | 阶段 2 只读向量列，总读量 = fetch_k × 标量列 + 存活行 × 向量列 |
| 输出列包含向量列（`SELECT vec ...`） | 向量列本就在读集（内核重排需要）；是否被 SELECT 不改变读集，只改变输出列序 |
| **向量列必读（内核精确重排）** | 任意阶段读集须含向量列；停读向量列需改距离来源（索引近似分），改变召回语义，非本方案范围 |
| **索引扫描输出契约** | 现有数据面契约描述为「全表列 + _distance」；收窄输出（层级 1/2 已按投影列输出）时契约文档需同步演进 |
| **含删除文件的数据文件** | 物化读路径对含删除文件（position/equality deletes）的文件直接失败（现状 PoC 限制）；命中时整体回退或报错，属现状约束，不因本方案改变 |
| 文件级裁剪已排除大部分文件 | 物化候选已少，收益相应小 |

## 6. 实现路线

### Phase 1 —— 列子集读能力（投影感知物化，层级 1 形态）

**目标**：引入物化列子集读能力，读集从「全表列」收窄到「输出列 ∪ 向量列」（层级 1 语义）。谓词不入引擎，语义与现状完全一致。**向量列保留**（内核精确重排需要）。这一步独立产出「停读无关列」的有限收益，同时为层级 2 备好就绪的列子集读能力（层级 2 不依赖本阶段，但能力复用）。**为何层级 2 不依赖本阶段却仍先做**：层级 2 可直接跳过本阶段实现（其两阶段本身就是列子集读）；本阶段独立存在的价值有二——① 谓词不可下推（或暂未接入谓词）的查询仍能停读无关列；② 作为低风险分步，先在无谓词形态验证列子集读能力、隔离改造风险，再叠加谓词编排。

- 读原语：增加列投影参数；物化读列 = 输出列 ∪ 向量列。
- 窄读走通用读取路径（快速路径自动退回）。
- 引擎按已知读集收窄物化读列，输出结构不变（投影 + 距离列由内核重算）。

**验证**：正确性（优化前后结果集逐行一致）+ 读量对比 + 性能 A/B（§7）。

### Phase 2 —— 层级 2：标量先行

**目标**：标量谓词进引擎，先读标量列过滤，存活行再读输出列与向量列。

- FDW：本地谓词序列化为 `scalar_filter` 进向量索引配置（复用表达式 JSON 格式）。
- 桥接：解析 + 透传。
- 引擎：两阶段物化编排 + 谓词求值（精确或超集，§5.2）。
- 读原语：阶段 1 窄读标量列、阶段 2 窄读（输出列 ∪ 向量列 − 标量列），按候选序重排拼接。
- 内核 VectorSearch 只见到存活行（引擎已过滤）——被过滤行不读向量列，这是层级 2 收益的核心。

**验证**：过滤率梯度 A/B + 正确性断言（与 recheck 全量比对，§7）。

## 7. 验证与验收（端到端整体收益）

> 验收口径为**端到端整体收益**（不按层级分层测试）：同一条 SQL，现状 build vs 优化 build 的总延迟对比，按实测过滤率分档。

### 7.1 数据

- **数据集**：SIFT-100 万（128 维）、GIST-100 万（960 维），现有测试文件目录。
- **追加受控标量列 `cat`**：`cat = 行号 % 10`（10 个均匀桶）——现状表无标量列，需扩展数据导入脚本追加列（需求文档 §4.1 已规划该改造）。

### 7.2 SQL（优化为引擎内部透明改动，基线/优化同一条）

查询向量从官方 query set 抽样；过滤率档用**范围谓词**控制（`cat` 均匀分布 10 桶 → 候选内近似均匀 → 存活率 ≈ 命中桶数 / 10）：

```sql
-- 对照：无过滤（确认无回归）
SELECT id FROM t ORDER BY vec <-> '<q>'::vector LIMIT K;

-- 过滤梯度：~10% / ~20% / ~50% / ~80% / ~90%
SELECT id FROM t WHERE cat = '1'   LIMIT K;   -- 1 桶 ≈ 10%
SELECT id FROM t WHERE cat >= '8'  LIMIT K;   -- 2 桶 ≈ 20%
SELECT id FROM t WHERE cat >= '5'  LIMIT K;   -- 5 桶 ≈ 50%
SELECT id FROM t WHERE cat >= '2'  LIMIT K;   -- 8 桶 ≈ 80%
SELECT id FROM t WHERE cat >= '1'  LIMIT K;   -- 9 桶 ≈ 90%
```

等值 / 范围（=、<、<=、>、>=）均属可下推谓词（§5.2 支持集），正是优化生效的形态。

> **IN 暂不可下推**（2026-08 实现期核实）：FDW 谓词翻译只处理 OpExpr / NullTest，ScalarArrayOpExpr（IN）不进入 `sdk_filter` / `scalar_filter`，走本地 recheck。故过滤梯度用范围谓词等价表达；IN 下推属后续增强（引擎求值器已支持 `ScalarOperator::In`，仅差 FDW 侧翻译）。

### 7.3 A/B 方式

- **两个 build**：现状 vs 优化（实现路线 §6 后），同机、同索引工件（同 nprobe / 码本）、同 DOP {1, 8}、同查询向量集合。
- K {1, 10, 100}；每档 ≥3 轮平均，记录 P50/P99。
- **引擎埋点输出每次查询的 `(fetch_k, survivors)`**——按**实测候选内存活率**分组报告（不假设 IN 宽度 = 存活率；ANN 候选有偏，以实测为准）。

### 7.4 指标与预期

- **主指标**：端到端延迟加速比（优化 / 现状），按 K × 实测存活率档出表。
- **预期形态**：低存活率档（~10%）加速最大（向量列读量降 ~10 倍）；高存活率档（~90%）接近现状或略慢（两阶段多一次窄读 + 过滤求值开销）；**GIST 收益 > SIFT**（960 维向量列占宽比大）。
- **无回归**：0%（无过滤）与高存活率档不得劣化（两阶段在 0% 过滤时读量退化为单阶段，仅多微小求值开销，需实测确认）。
- **正确性**（devtest 断言）：优化前后 `ORDER BY vec <-> q LIMIT K` 结果集逐行一致（行、顺序）；引擎过滤与 recheck 全量比对无假阳性、无漏行；边界：无标量谓词、过滤率 0%、输出列 == 标量列、输出列含向量列、存活行 < K、含删除文件回退。

### 7.5 测试前基建缺口

1. **cat 列追加**（数据导入脚本扩展）。
2. **引擎 fetch_k / survivors 埋点**（解释收益幅度 + 按实测存活率分组）。
3. **优化 build**（实现路线 §6：列子集读 + 标量先行）。

## 8. 与候选集预过滤的关系

- 本方案只优化**物化**（读列收窄 + 两阶段），**不改变候选集生成**——候选集仍由向量检索的 fetch_k 决定。
- 「索引级候选集预过滤」（用标量索引枚举/过滤候选集、下推向量检索）是另一类独立改进，与本文**互补可叠加**：候选集预过滤让「进入物化的候选行更贴合标量条件」，本文让「物化本身更便宜」。两者可独立评审、独立落地。
- 本方案落地后，现状 post-filter 路径的物化基线整体下移，混合查询的现状性能参考同步更新。
